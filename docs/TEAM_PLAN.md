# PIKKU 팀 역할과 v1 인계

상태: v1 개발 기준 공유 | 2026-10-31. 역할은 사용자가 명시한 최신 분담을 반영한다. 기존 담당 분담은 유지하고, v1 기준으로 바로 연결할 산출물을 아래 표에 정리했다. 제품 범위는 [PRD](PRD.md), 회의 근거는 [회의 맥락](MEETING_ALIGNMENT.md)을 따른다. 연결 저장소는 [codyssey-hackathon-bbikku](https://github.com/codyssey-hackerton/codyssey-hackathon-bbikku)이며 작업 진행·완료의 정본은 GitHub Issues와 마일스톤을 사용할 예정이다. 기술 인계는 [아키텍처](ARCHITECTURE.md)와 [최소 계약 v1](CONTRACTS.md)을 검토하며 맞춘다.

## 지금 병렬로 진행할 인계

| 담당 | 지금 필요한 산출물 | 기준 / 남은 결정 |
|---|---|---|
| 세진 | Expo·Fastify·LangGraph 기본 E2E, 공유 타입·API, 승인/버전 검증과 통합 | CONTRACTS v1. 제공자 PoC를 기다리지 않고 시작. |
| 찬욱 | PostgreSQL 일정/Memory/Proposal/Approval/연락작업 저장·조건부 트랜잭션, 연결 환경 | CONTRACTS §2·5·7. 호스팅/VM·접속·보존기간은 검증 후 확정. 비밀키 제외. |
| 영휘 | 한 S LLM 시스템 프롬프트, §3 읽기/계산 Tool, 정상·질문·개인화·무변경·연락 예외 평가 | Terra/high 기준. Tool 검증이나 승인 권한을 프롬프트만으로 해결하지 않음. |
| 서연 | 앱용 Calendar/Gmail OAuth 및 실제 송수신 조건, 전화 양방향 한국어 음성, 이동시간 제공자 검증 | ARCHITECTURE §7·CONTRACTS §7. 후보/실제 시도/성공/불명 구별. |
| PM(홍빈) | 세 화면, 개인 승인·연락 승인·응답 대기/실패 UX, §2 시연 대본과 QA | 최종 기기/연락 채널·범위 축소는 세진과 실제 검증 결과로 결정. |

각자는 독립 서비스를 새로 만들기보다 위 계약에 연결되는 결과물을 준비한다. 입력·출력, 실제 확인 결과, 미검증, 필요한 결정만 간결하게 공유한다. 공통 계약 변경은 세진과 먼저 맞춘다. 아래 역할 상세의 초기 준비 제안은 이 v1 표를 우선해 해석한다.

## PM — 기획·디자인·일정·QA 총괄

- **범위:** 전체 기획, PRD와 우선순위 검토, UX/UI 시안, 일정·QA 및 제출 총괄.
- **다음 모임 전 준비 제안:** 핵심 사용자·시연 흐름과 P0/P1/P2를 검토하고, 시나리오별 화면 흐름과 질문·승인 UX의 판단이 필요한 부분을 정리한다.
- **인계:** 검토된 PRD의 변경 사항, UX/UI 시안과 화면별 행동, QA 시나리오 및 미결정 항목을 세진님과 관련 담당자에게 전달한다.
- **선행 의존성:** 회의·멘토링 원문과 공식 제출 가이드 확인, 세진님의 구현 가능성 검토, 담당자들의 제약 확인.
- **통합 전 검증:** 제품 흐름·인수 기준의 모순, 추천과 확정의 구분, 근거 및 공식 제출 조건을 확인한다. 미검증은 표시한다.
- **제외:** 전체 프론트엔드·백엔드 코드 구현의 주 책임이나 기술 아키텍처 단독 확정.

## 세진님 — 앱·백엔드·아키텍처·통합

- **범위:** 프론트엔드와 백엔드 전체 구현 주도, 앱·시스템 아키텍처, 빌드 환경과 다른 담당자 산출물의 통합.
- **다음 모임 전 준비 제안:** 제안된 핵심 시나리오의 구현·시연 가능성과 플랫폼 후보, 앱·서버·외부 연결의 위험을 검토한다. 매시간 상태 확인·다음 날 정기 추천·이벤트 기반 재추천은 서버 실행, AI 호출 조건, 앱 표시와 실제 알림을 구분해 난도와 시연 가능성을 검토한다. 전날/아침 서버 트리거는 v1 목표이고 푸시 전달은 미정이다.
- **인계:** 기술 후보와 제약, 최소 통합 경계, 필요한 입력·출력 및 실행·검증 방법을 PM과 각 담당자에게 공유한다.
- **선행 의존성:** PM의 제품 우선순위와 UX 시안, 찬욱님의 데이터·VM 검토, 영휘님의 AI 규칙, 서연님의 외부 연동 검증.
- **통합 전 검증:** 연결되는 각 산출물의 입력·출력, 실행 조건, 실패 및 미검증 항목을 확인하고 실기기·시연 환경의 가능성을 점검한다.
- **제외:** 다른 담당자의 전문 검토 결과를 검증 없이 대신 확정하거나 모든 제품 우선순위를 단독 결정하는 것.

## 찬욱님 — DB·Long-term Memory·제공 VM

- **범위:** 데이터 모델·저장과 사용자 선호·행동 기록·장기 메모리 접근, 제공 VM 사용 가능성 검토.
- **다음 모임 전 준비 제안:** 필요한 데이터 범주와 메모리 구분, VM 자원·접근·종료 시점 확인 방법을 검토한다. VM 접속·설정 변경은 승인과 접근 정보 확인 후에만 수행한다.
- **인계:** 세진님에게 데이터·Memory의 필요한 입력·출력, 접근 조건, 설정과 검증 결과·미확인 사항. 공유 타입은 CONTRACTS v1, 실제 테이블은 담당자가 정해 세진과 맞춘다.
- **선행 의존성:** PRD의 개인정보·기능 범위, 세진님의 통합 경계, 실제 VM 가이드와 접근 권한.
- **통합 전 검증:** 사용할 수 있는 데이터와 저장·조회 결과, 선호와 행동 관측의 구분, VM 접근·자원·가용성 및 장애 가능성을 실제 확인한 범위만 보고한다.
- **제외:** 앱·백엔드 전체 구현 및 통합 책임, 확정되지 않은 인프라의 독단적 결정.

## 영휘님 — 시스템 프롬프트·AI 가이드라인

- **범위:** 사용자 맥락 이해, 추가 질문, 추천·승인·거절·재추천, 도구 사용 및 가드레일에 관한 프롬프트와 행동 지침.
- **다음 모임 전 준비 제안:** PRD의 필수 시나리오와 예외를 이용해 가이드라인과 테스트 사례를 준비한다.
- **인계:** 세진님에게 프롬프트·가이드라인, 필요한 입력과 기대 출력, 테스트 사례·결과, 실패 사례 및 미검증 사항.
- **선행 의존성:** PM의 제품·승인 원칙, 세진님의 실행 경계, 찬욱님의 사용 가능한 맥락과 서연님의 외부 도구 제약.
- **통합 전 검증:** 정보 부족·무응답·거절·영향 없음·제3자 연락 승인 사례를 점검하고, 계산값을 임의로 꾸미지 않는지 확인한다.
- **제외:** 전체 앱·서버 코드와 기술 스택 단독 확정, 검증하지 않은 AI 성능의 보장.

## 서연님 — 외부 API·음성·실제 전화 검토

- **범위:** 캘린더·지도·교통 등의 외부 API, 앱 내 음성과 사용자·제3자 대상 실제 발신의 가능성 검토.
- **다음 모임 전 준비 제안:** 연동별 지원·권한·비용·개발시간과 장애·시연 제약을 조사한다. 네 종류인 알림, 앱 내 음성, 사용자 발신, 제3자 발신을 구분한다.
- **인계:** 세진님에게 API 사용 조건, 입력·출력, 인증 방식의 안전한 참조, 테스트 결과·오류 및 미검증 항목을 전달한다. 비밀값은 전달 문서에 쓰지 않는다.
- **선행 의존성:** PM의 기능 우선순위, 세진님의 플랫폼·통합 방식, 실제 접근 권한과 제공자 조건.
- **통합 전 검증:** 접근 권한, 호출 결과, 비용·제한과 장애 대응을 실제 확인한 범위만 보고하고, 실제 발신과 제3자 승인 요구를 구분한다.
- **제외:** 외부 연동의 구현 완료 보장, 앱·백엔드 전체 구현 또는 사용자 승인 없는 제3자 연락.

## 준비 단계와 일정

2026-11-01 사용자 제공 최종 참가자 가이드 PDF 원문을 확인했다. 팀명은 **시계는 워치**, 최종 제출은 **2026-11-01 13:00 한국시간**이다. PDF 발표자료·2분 이내 MP4·GitHub URL과 최종 커밋 해시를 팀별 Google Drive에 제출한다. 1차 심사는 11-01, 2차 대면 심사는 11-02이며 세부 체크리스트는 [제출 안내](SUBMISSION.md)를 따른다.

진행 순서: ① v1 문서·계약 PR 공유 → ② 계약 기준 구현과 제공자 검증 병렬 진행 → ③ 세진님 중심 통합 → ④ 실제 시연 범위 확정·통합 QA → ⑤ 공식 규정 대조 및 제출. 내부 마일스톤과 담당별 Issue는 아직 확정하지 않았다. 전체 통합 QA를 다섯 명이 함께 수행하는 방향은 논의사항이며 세부 일정은 미정이다.

기술 검토는 기획 문서의 최종 확정을 기다리지 않고 담당자별로 병렬 진행할 수 있다. 가정과 미결정을 표시하고 결과를 세진님과 공유하며, 제품 범위나 공통 계약을 독단적으로 확정하지 않는다.

## 다음 모임을 위한 인계 형식 제안

각 결과는 하나의 간결한 메모 또는 기존 문서의 관련 부분으로 전달해도 된다. 공통으로 **입력·출력 또는 사용법, 확인 환경과 결과, 미검증·제약, 세진님이 필요한 다음 판단**을 적는다. 아래는 산출물 예시이며 별도 파일 생성이나 일정 확정은 요구하지 않는다.

| 담당 | 검토 및 전달 형식 |
|---|---|
| PM | 핵심 E2E 흐름과 화면 시안 링크 또는 설명, 기능별 기본·로딩·오류·빈 상태·질문·제안·승인·거절 등 필요한 UI 상태, 각 흐름의 QA 입력과 기대 결과·미결정 사항. 세진님과 공유. |
| 세진님 | 모바일 플랫폼 후보별 실기기·빌드·시연 가능성과 제약, 구성요소와 연결 흐름을 담은 아키텍처 초안, 최소 E2E 실행 구조 및 통합 위험·검증 결과를 PM과 담당자에게 공유. 채택 기술은 ADR v1, 미정/미검증만 후보로 표시. |
