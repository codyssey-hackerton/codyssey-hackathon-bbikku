# PIKKU 제품 요구사항 — 초안

상태: PM·팀 검토 전 | 2026-10-31 | 소유: PM

이 문서는 제품 요구사항의 정본 후보이며 **구현 완료 명세가 아니다**. 출처는 [회의 맥락 정렬](MEETING_ALIGNMENT.md)의 S1~S5 및 M01–M16. 실제 회의 녹취·기존 v0.3·공식 가이드는 미확인이다. 기능, 우선순위, 예시 인수 기준은 팀 승인 전 제안이며 자료가 추가되면 갱신한다.

2026-10-31 QA 반영: 기존 F01–F12 식별자를 유지하고 최소 시연 범위와 흐름을 구체화했다. 이후 S5 통합 회의록 정리본 전체를 읽고 US-01~US-14, 기능 후보 A~J 및 시나리오 A~F를 대조해 누락된 세부 논의를 보존했다. 정리본과 녹취 원문은 다르다. [회의 맥락](MEETING_ALIGNMENT.md)의 대조표를 참조한다.

## 1. 개요와 제품 목표

사용자가 일정을 적은 뒤에도 준비·이동·작업 순서를 판단하고 지연에 대응해야 하는 부담을 줄인다. 삐꾸는 일정·할 일·루틴과 개인 맥락을 바탕으로 실행 가능한 계획과 다음 행동을 제안하고, 계획이 어긋나면 필요한 부분의 복구를 돕는 것을 목표로 한다. [M02–M11]

대상 후보는 일정과 개인 작업을 병행하는 학생·직장인 등이다. 어느 집단을 MVP의 우선 사용자로 삼을지는 **미정**이다. 이들의 공통 니즈는 적은 입력으로 실현 가능한 계획을 세우고, 바뀐 상황에서도 스스로 최종 선택하며 작업을 이어가는 것이다.

Plan(계획), Act(실행), Recover(복구)는 가치를 설명하는 작업용 구분이며 공식 슬로건은 미정이다. 차별화 가설은 사용자별 준비시간·선호와 일정의 성격을 반영하고, 영향이 없는 경우에는 변경하지 않으며, 미완료를 다시 이어가도록 돕는 경험이다. 효과와 경쟁 우위는 아직 측정되지 않았다. [M03–M11]

## 2. 범위와 우선순위

**P0/P1/P2는 작성자의 개발 우선순위 제안이며 팀이 승인한 MVP가 아니다.** P0는 핵심 시연을 위한 제안, P1은 핵심 경험을 보완하는 제안, P2는 타당성과 범위를 별도 검토할 확장 후보다. 제공·완료·검증 여부는 모두 미확인이다. 외부 연동의 성공을 P0 완료 조건으로 가정하지 않는다.

|---|---|---|---|
| F01 | 최소 선호 입력, 나머지는 점진적 수집 | P0 최소 입력; 선호 관리 확장 P1 | M01, M03 |
| F02 | 고정 일정 1건과 유동 작업 1건 및 상태 표시 | P0 최소; 전체 캘린더·반복 루틴 P1 | M02, M13 |

| F12 | 외부 연동·위치·음성·전화 등 확장 | P2 | M12, M14, M15 |

**범위 밖 / 확정 아님:** 팀 승인 없는 모든 기능의 구현 보장, 승인 없는 일정 변경 또는 제3자 연락, 기술 방식이나 특정 외부 연동의 채택. 시연에 포함할 실제 범위와 타깃은 미정이다.

**최소 E2E 제안 — 팀 승인 전:** 사용자가 명시적 선호와 일시적 상황, 준비시간·이동시간·도착 여유를 입력하고 고정 일정과 유동 작업을 등록한다. 사용자의 요청으로 AI가 맥락을 반영한 작업 계획과 이유를 생성한다. 일정 충돌·시간 계산·고정 일정 보호를 검증한 제안을 사용자가 승인하면 반영하고, 앱에서 다음 행동을 확인하거나 수동으로 완료·미완료를 표시한다. 같은 시나리오에서 지연을 직접 입력해 영향 없으면 유지하는 경우와 단일 미완료 작업의 유효성을 확인해 복구 대안을 승인하는 경우를 검증한다. 복잡한 반복 규칙, 자동 트리거, 실시간 외부 정보와 음성·전화는 필수가 아니다. 세진님의 실현 가능성 확인과 PM 승인이 필요하다.

| 검토 구분 | 범위 제안 |
|---|---|
| 반드시 동작할 P0 후보 | F01~F07의 최소 입력·맥락 기반 AI 제안·검증·승인, F09의 앱 내 표시·수동 체크인, F10의 단일 지연 영향 확인, F11의 단일 작업 복구. 실제 AI 응답과 상태 변경을 확인한다. |
| 흐름을 설명할 UI | 최소 입력·일정, 추천과 이유, 검증 실패·정보 부족, 승인·거절, 다음 행동과 미완료 상태를 확인할 수 있는 화면. 화면 수·디자인은 확정하지 않으며 설명용 시안만으로 동작 완료를 판정하지 않는다. |
| 확장 및 일반화 P1/P2 | 반복 루틴 전체, 여러 작업과 복잡한 재계획, 행동 관측 기반 학습, 자연어 조회, 정기·이벤트 트리거, 푸시와 외부 연동 등은 각 기능의 P1/P2·백로그 제안을 따른다. |
| 외부 API 선행 검토 | 서연님이 인증·비용·권한·실기기 제약 등을 병렬 검토할 수 있다. 검토 결과는 후보 선정의 근거이며 실제 연동을 P0의 완료 조건으로 만들지는 않는다. |
| 별도 결정할 후보 | 자연어 조회의 P0 포함, 자동 트리거·실제 알림, 외부 API 또는 전화의 시연 포함, 데이터 저장 범위와 시연 플랫폼은 PM·팀과 세진님이 별도 결정한다. |

한 명의 주 개발자가 지연 판단과 복구까지 끝내기 어려운 경우, 먼저 **맥락 기반 추천 → 검증 → 승인 → 앱 내 표시**를 완성하고 F10·F11을 후속 범위로 조정하는 축소안을 PM·세진님이 검토할 수 있다. 이는 일정 위험에 대한 대안이지 현재 P0 제안을 바꾼 결정이 아니다. 변경 시 두 기능의 우선순위와 시연 범위를 팀이 다시 승인한다.

F08의 자연어 **조회**는 AI 경험을 보여주는 유력 후보지만 한 명의 통합 개발 부담을 고려해 우선 P1로 둔다. 세진님이 최소 E2E에 무리 없이 통합 가능하다고 확인하면 PM이 P0로 조정할 수 있다. 외부 API·전화의 조기 기술 검토는 서연님이 진행할 수 있으나, 검토 우선순위는 제품 구현 우선순위와 다르다. P0의 지연·복구도 단일 사례만 제안하며 포괄적 자동 재계획을 요구하지 않는다.

## 3. 통합 유저스토리

S5 §4의 US-01~US-14를 [대조표](MEETING_ALIGNMENT.md)에 각각 연결했다. 아래는 이를 통합한 **후보**이며 원본 스토리의 세부사항과 확장 아이디어는 대조표·기능 명세·백로그에 보존한다.

1. 처음 쓰는 사용자는 필요한 정보만 입력하고 나중에 선호를 수정해, 입력 부담을 줄이고도 개인화된 제안을 받고 싶다. [M01, M03]
2. 학생·직장인은 일정, 해야 할 일과 반복 루틴을 하루 흐름에서 보고 고정된 약속과 유동적인 작업을 구분하고 싶다. [M02, M10]
3. 사용자는 자연어로 일정을 요청하고, 추천에 필요한 정보만 추가로 답하고 싶다. [M05, M08, M13]
4. 외출을 앞둔 사용자는 자신의 준비시간과 이동·도착 여유에 맞춰 준비·출발 시각을 알고 싶다. [M04]
5. 사용자는 일정 충돌과 추천 이유를 살펴보고, 수락·거절·수정한 뒤에만 변경 사항을 반영하고 싶다. [M06, M07]
6. 사용자는 적절한 시점에 다음 행동을 안내받고 실제 수행 여부를 기록하고 싶다. [M09]
7. 늦잠을 잔 사용자는 일정에 영향이 없다면 기존 계획을 유지하고, 영향이 있다면 필요한 부분에 한해 대안을 받고 싶다. [M10]
8. 운동을 놓친 학생은 학교의 고정 일정을 지키면서 운동을 다시 할 수 있는 시간을 제안받고 싶다. [M11]
9. 미완료 작업이 있는 사용자는 기한이나 필요 여부를 확인한 뒤 유효한 작업만 다시 계획하고 싶다. [M11]
10. 중요한 발표를 앞두고 피곤한 사용자는 휴식 또는 약속 조정 제안을 검토하되, 본인 승인 없이 일정이 바뀌거나 상대에게 연락되지 않기를 원한다. [M12]
11. 사용자는 위치가 불명확하거나 외부 정보가 없을 때 잘못된 확정을 받지 않고 상황을 확인할 수 있기를 원한다. [M14, M15]
12. 사용자는 정기적으로 다음 날을 준비하고, 추천을 거절한 이유를 선택적으로 전달해 이후 더 적절한 추천을 받고 싶다. [S5 US-02, US-04]
13. 사용자는 하루 활동과 목표 대비 결과를 회고하고, 퀘스트·보상 등으로 실행을 지속할 동기를 얻고 싶다. [S5 US-13, US-14; 확장 백로그]

## 4. 기능 요구사항과 검증 기준

각 항목의 입력·처리·출력과 AC는 **제안된 제품 동작**이다. 같은 F 항목 안의 전체 기능과 AC가 모두 P0라는 뜻은 아니다. P0 최소 범위는 §2의 표와 최소 E2E 제안을 따르며 나머지는 표·본문의 P1/P2 또는 백로그에 따른다. ‘확인’은 사람이 결과를 비교할 수 있는 기준을 뜻하며 현재 구현이나 통과를 뜻하지 않는다.

### F01 — 온보딩과 선호 [P0 제안; M01, M03]

- **의도:** 최초 입력 부담을 줄이면서 이후 필요한 맥락을 확보한다.
- **입력:** 호칭, 생활 패턴, 활동 유형, 목표, 장소·이동 선호·루틴 등 후보. 최초 필수값은 미정.
- **처리:** 필수로 확정되지 않은 항목은 나중에 입력할 수 있게 하고, 선택과 자유 입력을 제공하며 수정 가능하게 한다.
- **출력:** 입력된 선호와 미입력 상태, 필요할 때의 추가 질문.
- **P0 최소 AC:** 준비시간 등 시연에 필요한 선호를 입력할 수 있고, 최초 필수로 정해지지 않은 장소를 비워도 계속할 수 있다. 최초 필수 항목은 PM 승인 필요.
- **P1 확장 AC:** 사용자가 저장된 준비시간 선호를 수정하면 이후 추천에 변경된 값이 사용된다.
- **추가 후보 [S5 A, US-01]:** 사용자 가입 또는 식별, 연령대·서비스 목적 등 선택 입력, 집·학교·회사 등 여러 장소와 목적의 등록·수정·삭제, 여러 루틴, 외부 서비스 접근 동의·권한 요청. 식별 방식·수집 항목·요청 시점은 미정이다. 건너뛴 선택 항목은 나중에 등록할 수 있어야 한다.

### F02 — 일정·To-do·루틴 [P0 제안; M02, M13]

- **입력:** 제목·시간 또는 예상 소요, 고정/유동, 개인/타인 참여, 반복 및 완료 상태 등 해당되는 정보. 필수 필드·정확한 데이터 계약은 미정.
- **처리:** 일간 흐름에서 일정과 작업·루틴 및 추천 상태를 구분한다. 반복 규칙과 특정 회차 수행 상태는 구분한다.
- **출력:** 날짜별 일정과 하루 타임라인, 등록·수정·삭제 결과, 완료·미완료 상태.
- **P0 최소 AC:** 같은 날 고정 미팅과 유동 청소를 각각 한 건 등록하고 유형을 확인할 수 있다. 제안·승인된 일정 및 완료·미완료 상태는 구별된다.
- **P1 확장 AC:** 특정 날짜의 운동을 미완료로 기록해도 반복 규칙 자체가 삭제되지 않는다.
- **범위 후보 [S5 B, G, US-07·09]:** 중요도·참여자·예상 소요시간, 요일·시간에 따른 루틴 등록·수정 및 수행 기록. 타임라인·루틴 화면을 반드시 별도 탭으로 만들지는 미정이다. 외부 캘린더 조회와 변경은 F12에서 별도 권한을 검토한다.

### F03 — 개인화 맥락 [P0/P1 제안; M03, M04]

- **입력:** 명시 선호, 현재 일정, 실제 행동 기록, 추정 패턴, 일시 상황 중 사용 가능한 정보.
- **처리:** 출처와 성격을 구분하고, 기록이 없으면 관측된 사실처럼 표현하지 않는다. 실제 수집 및 보관 범위는 미정.
- **출력:** 추천에 반영한 정보와 부족하거나 불확실한 정보.
- **P0 최소 AC:** 동일 일정에 준비시간 15분과 45분을 각각 입력하면 다른 준비 시작 시각을 제시한다. 행동 기록이 없는 사용자에게 관측된 행동에 기반한 추천이라고 표시하지 않는다.
- **P1 확장 AC:** 실제 수집한 행동 기록을 활용할 경우 명시 선호와 관측·추정을 구분해 보여주며, 관측하지 않은 행동을 사실로 제시하지 않는다. 수집·활용 범위는 미정이다.
- **피드백 후보 [S5 H, US-10]:** 명시 선호, 실제로 입력·관측된 실행 기록, 승인·거절 이력과 일시적 상황의 출처를 구분한다. 실제 관측된 반복 행동과 동의된 피드백의 개인화 활용, 필요한 정보만 선택 조회·오래된 정보 정리는 P1 이후 검토이며 수집·보존 방식과 기준은 미정이다.

### F04 — 추가 질문 [P0 제안; M01, M05, M13]

- **입력:** 현재 요청과 이미 제공된 관련 정보.
- **처리:** 현재 추천에 필요한 값이 부족한 경우에만 질문하고, 이미 확인된 값을 반복 질문하지 않는다. 선택지와 직접 입력을 지원한다.
- **출력:** 질문과 응답 또는 정보 부족 상태.
- **P0 최소 AC:** 시연에서 청소 소요시간이 추천에 필요하고 알려져 있지 않으면 질문한다. 이미 확인된 값은 다시 묻지 않으며, 무응답이면 값을 가정하거나 변경을 적용하지 않는다.
- **P1 확장 AC:** 다른 일정 유형에서도 필요한 정보만 질문하고, 기존 답이 유효할 때 재사용한다.

### F05 — 준비·출발 시각 [P0 제안; M04]

- **입력:** 약속 시각, 사용자의 준비시간, 이동시간, 도착 여유시간과 그 출처.
- **처리:** 출발 시각 = 약속 시각 − 이동시간 − 도착 여유; 준비 시작 = 출발 시각 − 준비시간. 알려지지 않은 값은 추측으로 확정하지 않는다.
- **출력:** 계산된 시각과 사용된 값; 값이 없으면 추가 질문 또는 계산 불가 안내.
- **AC:** 15:00 약속, 이동 30분, 여유 10분에서 출발은 14:20이다. 준비 15분이면 14:05, 45분이면 13:35다. 이동시간이 없으면 확정된 출발 시각을 임의로 제시하지 않는다. [S2 §2.1]

### F06 — 계획 추천 [P0 제안; M06, M12, M16]

- **입력:** 사용자 요청 또는 검토할 시간·상황, 일정·선호·필요한 맥락.
- **처리:** 충돌, 일정의 유연성, 가능한 여유와 현재 상황을 고려하여 계획과 이유를 제시한다. 정기 시각은 미정이며 21시는 예시다.
- **출력:** 기존 일정과 구분되는 제안, 이유·대안 또는 정보 부족 안내.
- **P0 최소 AC — 추천과 안전 검증:** 실제 AI 응답이 고정 일정, 유동 작업, 명시 선호와 사용자가 전달한 일시적 상황을 근거로 작업 계획과 이유를 제시한다. 시간 역산만 수행하거나 미리 작성한 고정 응답을 보여주는 것은 이 기준을 충족하지 않는다. AI 생성 실패·시간 초과·정보 부족 시 변경 없이 실패 또는 추가 확인 상태를 보여준다.
- **P0 최소 AC — 반영 전 검증:** AI가 제안한 시간은 서버 등 시스템 로직에서 충돌·준비/이동시간 계산과 고정 일정 보호를 검증한다. 검증 실패나 불확실성이 있으면 해당 안을 실행 가능한 확정안으로 표시하거나 반영하지 않고 충돌 이유를 안내하거나 추가 정보를 요청한다. 사용자가 수락한 후에도 현재 일정과 승인 대상이 바뀌지 않았는지 확인하고, 검증을 통과한 변경만 반영한다. 거절·무응답·승인 누락 또는 오래된 제안은 반영하지 않는다. 구체적인 구현 구성은 미정이다. [F05, F07, F10]
- **P1 확장 AC:** 다음 날과 그 이후 일정·생활 패턴을 종합한 정기 추천에서 피로 정보가 있으면 휴식 또는 일정 조정을 이유와 함께 제안할 수 있으며 승인 전 확정되지 않는다.
- **트리거 구분:** 사용자의 요청에 따른 즉시 추천은 최소 시연 제안이다. 정기적인 다음 날 추천은 별도 후보(P1)이며 사용자별 시각·동작은 미정이다. 21시는 예시로만 취급한다. [M16]
- **다음 날 추천 후보 [S5 C, US-02]:** 내일과 그 이후의 중요한 일정, 생활 패턴, 빈 시간 및 식사·휴식·이동을 참고한다. 추천이 가능한 경우 이유를 설명하고 F07에서 개별 제안을 검토한다. 그 이후 일정이나 상태가 없을 때 있다고 추측하지 않는다.
- **트리거 기술 검토 [P1 제안]:** 매시간 상태 확인, 정기적인 다음 날 추천, 일정 변경·지연 등 이벤트 기반 재추천은 선택사항이다. 세진님이 ① 정기적인 서버 실행과 상태 확인, ② 실제로 AI 판단을 호출할 조건, ③ 앱 내 결과 표시, ④ 사용자 기기에 전달되는 실제 알림을 각각 구분해 개발 난도·시연 가능성을 검토한다. 상태 확인마다 AI 호출이나 알림이 자동 발생한다고 가정하지 않는다. 21시는 예시이며 빈도·실행 방식·비용·실기기 제약은 미정이다. [S5 §8.2, 최신 QA 요청]

#### 맥락 기반 AI 추천 검증 사례 [P0 제안; F02·F03·F05~F07, S5 US-02·06·10]

이 사례의 구체적 시간과 상황은 회의 맥락을 바탕으로 만든 **QA 예시**다. 수치나 팀 합의로 확정된 시연 대본이 아니다.

- **공통 입력:** 오늘 15:00~16:00은 고정 회의, 개인 공부는 1시간짜리 유동 작업이며 18:00까지 완료해야 한다. 가능한 공부 시간은 10:00~11:00 또는 16:30~17:30이다. 명시적 장기 선호는 오전 집중 작업이다. 회의 준비·이동 입력은 F05 기준에 따라 따로 검증한다.
- **상황 A:** 사용자가 “오늘 오전은 피곤해서 쉬고 오후에 공부하고 싶다”고 말하면, AI는 제공된 상황과 선호·일정을 바탕으로 16:30~17:30 공부를 제안하고 오전 휴식과 고정 회의를 고려한 이유를 표시한다. 실제 관측하지 않은 수면·행동 기록을 근거로 말하지 않는다.
- **상황 B:** 같은 일정과 선호에서 사용자가 “오늘은 오전에 공부하고 싶다”고 말하면, AI는 10:00~11:00을 제안하고 그 상황과 선호를 반영한 이유를 표시한다. A와 B는 기존 선호를 같은 값으로 두고 일시적 상황만 바꾼다.
- **검증 결과:** 두 경우 모두 제안 시간은 사용자에게 제공된 가능 시간과 마감에 맞고 15:00~16:00 고정 회의를 침범하지 않아야 한다. AI의 설명은 실제 제공된 정보에 근거해야 하고 고정 회의는 그대로 둔다. 시간·충돌·고정 일정 검증을 통과한 제안도 수락 전에는 일정에 반영하지 않는다. 검증에 필요한 값이 없거나 충돌하는 결과를 생성하면 확정하지 않고 부족 정보 또는 오류를 안내한다. 승인 후 기존 일정이 바뀐 경우도 다시 확인한다.
- **역할 경계:** AI는 상황과 선택지를 해석해 계획·이유를 생성한다. F05는 입력값을 이용해 준비·출발 시각을 계산하고, 시스템은 시간·충돌·고정 일정·승인 여부를 검증한다. 특정 모델이나 Agent 프레임워크는 미정이다.

### F07 — 승인·거절·수정 [P0 제안; M07, M12]

- **입력:** 제안된 계획과 사용자의 수락·거절·수정 선택.
- **처리:** 제안을 확정 일정과 구분한다. 수정된 제안도 반영 전 사용자 확인을 받는다. 무응답이나 거절은 승인으로 취급하지 않는다.
- **출력:** 승인된 변경 결과 또는 변경되지 않은 기존 일정과 선택 상태.
- **AC:** 수락 전·거절 후·무응답 상태에서 기존 일정이 변경되지 않는다. 사용자가 수정해 확인한 변경만 반영한다. 승인 없이 제3자에게 연락하지 않는다. 적용 전 일정이 변경된 경우 기존 제안을 그대로 적용하지 않고 재확인을 요청한다.
- **거절 사유 후보 [S5 C, US-04]:** 추천별 거절 시 사유를 선택적으로 입력하고, 이후 개인화에 활용하는 방안은 P1 제안이다. 사유를 입력하지 않아도 거절할 수 있다. 이용·보관 및 수정 방법은 미정이다.

### F08 — 자연어 일정 조회·관리 [P1 제안; M08, S4]

- **입력:** 일정 조회·등록·변경에 관한 자연어 요청.
- **처리:** 사용자의 의도와 대상·시간을 해석하고 모호하거나 부족한 값은 확인한다. 실제 변경은 F07의 승인 경계를 따른다.
- **출력:** 조회된 일정 또는 해석된 내용과 확인 질문·변경 제안.
- **AC:** “내일 오전 10시에 청소”를 입력하면 청소와 날짜·시각을 확인할 수 있다. 어떤 일정을 변경하는지 모호할 때 임의로 다른 일정을 바꾸지 않는다.
- **조회 AC:** 사용자가 “내일 일정 알려줘”라고 요청하고 내일의 일정이 있으면 해당 날짜의 확인된 일정을 보여준다. 일정이 없으면 없음으로 표시하고 날짜가 모호하면 확인한다. 조회만으로 일정을 수정하지 않는다.
- **알림 변경 후보 [S5 US-11]:** “이 일정은 30분 전에 알려줘”와 같은 요청을 해석하고 대상과 시각이 모호하면 확인한다. 실제 변경 방식·확인 UX는 미정이며, 승인 여부는 F07의 변경 원칙에 따른다. 조회·추가·일정 변경과 구분해 다룬다.

### F09 — 실행 지원 [앱 내 표시·수동 체크인 P0, 자동 안내 P1 제안; M09, M16]

- **입력:** 승인된 계획, 해당 시각, 사용자가 제공한 수행 상태.
- **처리:** 준비·출발·작업 안내 또는 체크인을 제공한다. 알림 시각과 방식은 미정이다.
- **출력:** 다음 행동 안내와 사용자 응답에 따른 상태.
- **P0 최소 AC:** 승인된 준비 행동이 있는 화면에서 다음 행동과 시각을 볼 수 있으며 사용자가 직접 완료·미완료를 선택할 수 있다. 응답하지 않은 상태는 미확인으로 유지한다. 자동 푸시 전달은 최소 시연의 필수 조건이 아니다.
- **P1 확장 AC:** 정해진 준비 시각에 자동 안내를 제공하는 경우, 앱 표시와 실제 알림 전달 여부를 구분해 확인한다. 실제 알림 권한·전달 가능성은 별도 검증 대상이다.
- **확장 후보 [S5 E]:** 기본 일정 알림, 사용자 지정 시각, 단계별 준비 행동, 지연 안내와 실행 체크인. 사용자 무응답만으로 늦잠이나 미수행을 확정하지 않는다.

### F10 — 지연과 영향 판단 [P0 제안; M10, M16]

- **입력:** 늦잠·지연·신규 약속 등 사용자가 알린 변화, 현재 일정과 제약.
- **처리:** 고정 일정·타인 참여 여부와 시간 충돌을 고려해 실제 영향 범위를 확인한다. 영향이 없는 일정과 완료된 과거 일정은 임의로 변경하지 않는다.
- **출력:** 유지 판단 또는 영향받는 일정의 대안과 이유.
- **P0 최소 AC:** 사용자가 지연을 입력했어도 출근과 이후 일정에 영향이 없는 단일 사례에서는 하루 일정을 유지한다. 시연에서 고정 일정과 유동 작업 한 건에 실제 충돌이 생기면 해당 작업의 대안을 보여주고 승인 전에는 반영하지 않는다. 상태가 불확실하면 확인하고 승인 없이 변경하지 않는다.
- **P1 확장 AC:** 새 저녁 약속과 유동 공부가 겹치는 사례 등 여러 변경 상황에서 충돌과 대안을 보여주고 승인 전에는 변경하지 않는다.

### F11 — 미완료 작업·루틴 복구 [P0 제안; M11]

- **입력:** 미완료 상태, 반복 여부, 기한·유효성, 다른 고정 일정과 빈 시간.
- **처리:** 실제 미완료 여부와 계속 필요한지를 확인하고 가능한 대안을 제시한다. 모든 미완료를 자동으로 다음 날로 옮기지 않는다.
- **출력:** 미완료 기록, 재추천 또는 유효성 확인 요청.
- **P0 최소 AC:** 단일 미완료 작업의 수행 여부와 유효성을 확인하고 가능한 대안을 제안하며 F07 승인 후에만 반영한다. 기한이 지났거나 유효성이 불명확하면 확인 없이 재추천하지 않는다.
- **P1 확장 AC:** 반복 운동을 놓친 경우 9시 학교 일정을 유지하면서 해당 루틴 회차의 복구 대안을 제시한다.
- **확장 후보 [S5 G, US-08·09]:** 반복 실패에 따른 다른 대안, 요일별 루틴의 등록·수정과 특정 회차별 수행 추적. 반복 행동에서 신규 루틴을 제안하는 경우 관측 기준은 미정이며 사용자 선택 없이 루틴을 만들지 않는 방안은 검토 제안이다.

### F12 — 외부 정보·음성·전화 [P2 제안; M12, M14, M15]

- **입력:** 사용자가 허용한 외부 일정·지도·위치 정보 또는 음성·전화 요청.
- **처리:** 앱 알림, 앱 내 음성, 사용자 대상 실제 발신, 제3자 발신을 별개로 검토한다. 외부 정보 부재·오류·위치 부정확성을 실제 상태로 단정하지 않는다.
- **출력:** 확인된 정보 또는 권한·실패·불확실 상태. 제3자 연락은 사용자 승인 전 실행하지 않는다.
- **AC:** 위치 권한이 없거나 위치가 불확실할 때 일정 이탈을 확정하지 않고 확인을 요청한다. 외부 서비스 장애 시 확인되지 않은 이동시간을 확정된 값으로 표시하지 않는다. 실제 전화 구현·권한·비용·상대방 보호는 미검증이다.

| 별도 후보 | 필요한 검토 | 제품 관점 검증 기준 후보 |
|---|---|---|
| 외부 캘린더 | 지원 범위, 인증·권한, 동기화·비용 | 연결 거부 또는 실패를 표시하고 기존 일정을 임의 변경하지 않는다. |
| 지도·교통 | 지원 범위, 인증, 호출량·비용, 이동시간 정확성 | 응답이 없거나 오래되면 확정 이동시간으로 표현하지 않는다. |
| 위치 확인 | 위치 권한, 정확도와 백그라운드 제약 | 권한 없음 또는 불확실한 위치만으로 일정 이탈을 확정하지 않는다. |
| 앱 내 음성 | 기기 지원·마이크 권한·응답 지연 | 권한 거부 또는 인식 실패를 표시하고 입력을 확정하지 않는다. |
| 사용자 대상 실제 발신 | 통신 지원, 발신번호, 비용과 사용 동의 | 발신 가능 여부와 사용자 동의를 확인하며 실패를 표시한다. |
| 제3자 대상 실제 발신 | 통신 지원·비용, 사용자 승인 및 상대방 보호 | 발신 전 사용자 승인 없이는 연락하지 않으며 실패를 표시한다. |

이들은 각각 다른 의존성과 검증이 필요한 확장 후보이며 구현·지원 여부는 확인되지 않았다. 실제 전화와 앱 알림은 별개다.

외부 캘린더 **읽기와 수정은 서로 다른 권한**을 검토하며 여러 출처의 중복·충돌을 실제 변경으로 단정하지 않는다. 위치 후보에는 예정 목적지와 다른 방향, 취소 여부 확인과 불필요한 알림 제한이 포함된다. 교통수단·대중교통 출발 분석, 스마트워치 수면 데이터, 이메일 일정, 문자·DM, 식사·장소 추천용 별도 Agent도 S5의 확장 후보다. 외부 서비스 조작과 연락은 실행 전 사용자 승인 및 해당 권한 확인이 필요하다. [S5 I, US-12]

### 확장 백로그 [S4, 우선순위 제안 P2]

하루 완료 활동 요약, 목표 대비·카테고리별 활동 및 완료율, 반복 실패 분석과 다음 계획 개선·개인화 기억 갱신을 검토한다. 퀘스트·보상, 연속 수행, 캐릭터 성장, 친구와의 활동, 실패 피드백, 집중 방해 요소 관리도 후보로 보존한다. 반복 행동에서 새 루틴을 제안하는 경험과 주간·월간 계획도 확장 후보다. 사용자 승인·구체적 동작·데이터·범위는 미정이다. 명시적으로 입력한 선호를 실제 행동 관찰로 표현하지 않으며, 관측 데이터가 없으면 그 기반의 패턴을 주장하지 않는다. [S5 US-08~10, US-13~14, G·H·J]

## 5. 주요 사용자 흐름과 예외

**기본 흐름 [M01–M09]:** 간편 설정 → 일정·작업·루틴 등록 → 사용자 요청 또는 미정인 트리거로 추천 검토 → 부족한 정보만 질문 → 시간·충돌 확인 → 이유가 있는 제안 → 사용자가 수락·거절·수정 → 승인한 변경 반영 → 다음 행동 안내. 화면 분리 방식은 미정이다.

**복구 흐름 [M10–M11]:** 지연이나 미완료를 알림 → 실제 영향과 수행 상태 확인 → 영향 없으면 유지 / 영향 있으면 고정 일정을 고려한 대안 제시 → 사용자의 선택 후 반영 → 유효한 미완료 작업을 다시 계획한다.

**예외:** 정보 부족 시 질문 또는 계산 보류; 거절·무응답 시 기존 일정 유지; 일정 충돌은 명시; 과거 완료 일정은 임의 수정 금지; 외부 API 장애·권한 거부·위치 불확실 시 상태를 알리고 확정하지 않음; 오래된 제안은 재확인; 만료된 작업은 유효성 확인. 각 오류 메시지와 복구 방식은 UX 검토 후 확정한다.

### 흐름 1 — 최소 설정부터 추천 승인 [F01–F07, F09]

1. **입력·행동:** 사용자는 준비시간과 고정 약속 시각, 이동시간·도착 여유를 입력하고 유동 작업을 추가한 뒤 추천을 요청한다. 최초 필수 항목과 화면 구성은 팀 검토 사항이다.
2. **판단:** AI는 요청과 맥락을 해석해 해당 추천에 필수인 값이 누락되었는지 판단한다. 부족하면 F04로 질문하고 이미 확인된 값은 반복 질문하지 않는다.
3. **계산·검증:** F05의 산식으로 준비·출발 시각을 계산하고 고정 일정과 충돌을 확인한다. AI 설명은 계산 결과에 근거한다. 값의 출처가 불명확하거나 계산에 필수인 값이 없으면 시각을 확정하지 않는다.
4. **화면·승인:** F06은 기존 일정과 구별되는 제안·근거를 보여준다. F07에서 수락해야 일정에 반영된다. 거절·무응답은 기존 상태 유지, 수정 시 변경 내용을 다시 확인한다. 승인 뒤 F09에서 앱 내 다음 행동을 보여준다.
5. **수용 기준:** 15:00 약속·이동 30분·여유 10분에서 출발 14:20, 준비 15분이면 시작 14:05, 45분이면 13:35다. 수락 전에는 기존 일정이 바뀌지 않고, 부족 정보에 답하지 않거나 추천 생성에 실패해도 임의의 값이나 변경을 확정하지 않는다.

### 흐름 2 — 지연 후 유지 또는 부분 재추천 [F02, F07, F10]

1. **입력·행동:** 사용자는 늦게 일어났거나 일정이 지연됐다고 알린다. 기존 고정 일정, 유동 작업, 현재 시각과 필요한 소요시간을 확인한다.
2. **판단:** AI는 변화의 의미와 확인해야 할 상태를 해석한다. 정보가 불충분하면 질문하고, 단순히 늦었다는 사실을 충돌로 단정하지 않는다.
3. **계산·검증:** 남은 준비·이동 시간과 고정 일정, 충돌 여부를 확인해 영향을 받는 범위를 구분한다. 과거 완료 일정과 영향 없는 일정은 보존한다.
4. **화면·승인:** 영향이 없으면 유지 이유를 표시한다. 영향이 있으면 영향을 받는 항목·대안·근거를 보여주고 F07 승인 후에만 반영한다. 거절·무응답·오래된 제안은 기존 일정 유지 또는 재확인한다.
5. **수용 기준:** 30분 늦게 일어나도 모든 약속에 영향이 없으면 기존 하루 일정을 유지한다. 개인 공부와 새 약속이 충돌하면 해당 충돌을 보여주고 사용자 승인 전에는 어느 일정도 옮기지 않는다.

### 흐름 3 — 미완료 작업 또는 루틴 복구 [F02, F07, F09, F11]

1. **입력·행동:** 사용자는 체크인에서 작업 또는 특정 루틴 회차를 미완료로 표시한다. 수행 여부가 모호하면 확인을 요청한다.
2. **판단:** AI는 작업의 기한·필요 여부와 사용자가 확인한 상황을 살피고, 불명확하거나 기한이 지났으면 유효성부터 확인한다. 확인되지 않은 활동을 무조건 다시 추천하지 않는다.
3. **계산·검증:** 고정 일정, 소요시간과 가능한 시간의 충돌을 확인한다. 특정 회차의 미완료는 반복 규칙 자체의 삭제나 변경으로 취급하지 않는다.
4. **화면·승인:** 유효한 작업에 가능한 대안을 제시하고 승인 후 반영한다. 기한 경과·유효성 불명·가능 시간 없음·거절·무응답은 이를 표시하고 자동 이동하지 않는다.
5. **수용 기준:** 놓친 운동과 9시 학교 일정이 있을 때 학교 일정을 유지한다. 유효성과 가능한 시간이 확인되면 운동 대안을 표시하되 승인 전 반영하지 않는다. 기한이 지난 작업은 유효성 확인 없이 재추천하지 않는다.

AI는 의도·맥락 해석, 필요한 질문과 설명을 돕는다. 시간 역산, 충돌·고정 일정·승인 여부 확인은 결과를 비교할 수 있는 검증 대상이다. 이 책임 구분은 제품 요구이며 특정 기술이나 구성요소를 확정하지 않는다. [S2 §9]

## 6. 성공 확인과 미결정

시연 후보는 초기 설정 → 일정 등록 → 개인화 추천 → 승인 → 실행 지원 → 지연·미완료 → 재추천이다. 동일 약속에서 사용자 A/B 준비시간을 비교할 수도 있다. 최종 시연과 달성 여부는 미정·미측정이다. [M03–M11]

확인할 증거 후보: 사용자별 입력이 추천에 반영되는지, 계산 결과가 주어진 값과 일치하는지, 승인 전 변경이 없는지, 영향이 없는 경우 유지되는지, 미완료 유효성이 확인되는지. 수치 목표와 측정 결과는 **미정 / 미측정**이다.

PM·팀이 결정할 항목: MVP 타깃과 범위·P0/P1/P2, 온보딩 필수값과 질문 시점, 추천 트리거·무응답·수정 정책, 실행 지원 방식, 사용자 데이터 수집·수정 범위, 외부 기능의 채택 여부. 통합 정리본 14개 스토리는 대조했으나 실제 녹취와 세부 합의의 확인 여부는 별개다. 플랫폼·저장·AI·외부 연동 등의 기술 선택은 별도 아키텍처 검토에 남긴다.
