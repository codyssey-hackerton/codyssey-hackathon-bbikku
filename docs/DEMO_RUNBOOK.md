# 합성 데이터 시연·QA

이 문서는 **시연 절차와 기대 결과**다. 전체 흐름의 구현 완료나 시연 성공 기록이 아니다. 개인화 추천 → 검증 → 승인 → 다음 행동 → 영향 없는 지연 → 미완료 복구를 순서대로 확인한다. 기능이 없거나 기대 결과가 다르면 해당 단계에서 중단하고 미구현·실패로 기록한다.

## 격리와 사전 확인

- 원본 서버·앱·DB 대신 별도의 합성 테스트 환경을 사용한다. 가상 시각은 테스트에 주입하며 시스템 시각은 바꾸지 않는다. 실명·실제 일정·이메일 주소는 사용하지 않는다.
- 자동 검사의 고정 모델 응답은 제안·승인 경로를 검증하는 모의 결과다. 실제 AI의 개인화 품질을 증명하지 않는다. 아래 시간은 `Asia/Seoul` 기준이다.
- 기존 합성 HTTP/메모리 테스트를 워크트리 루트에서 실행한다. 테스트용 DB 변수를 제거하며 임의 포트의 테스트 서버를 사용한다.

```sh
env -u PIKKU_TEST_DATABASE_URL -u PIKKU_DATABASE_URL -u PIKKU_OPENAI_API_KEY \
  -u PIKKU_GOOGLE_OAUTH_CLIENT_ID -u PIKKU_GOOGLE_OAUTH_CLIENT_SECRET \
  node --import tsx --test apps/api/test/mobile-integration.test.ts \
  apps/api/test/planning.test.ts apps/api/test/contact.test.ts
```

이 검사는 기존 제안·승인·체크인·연락 승인 경계의 일부를 확인한다. 아래 F09~F11 전체 시나리오나 실제 모델·PostgreSQL·Gmail 검증을 대신하지 않는다. 통합 화면에서 별도 가상 시각/모의 모델을 제공하지 않으면 해당 수동 단계는 **미검증**으로 남긴다.

F01~F08의 별도 합성 평가기는 `node --import tsx scripts/verify-core-flows.ts --self-test`로 모의 경로를 확인한다. 프로젝트 키가 실행 환경에 설정된 경우 `--live`는 격리된 메모리 데이터로 최대 4개 대화, 각 최대 6회 모델 호출을 수행한다. 청소 소요시간 질문과 답변 재사용, 준비 15/45분 역산, 내일·빈 날 조회, 모호한 날짜 확인을 다룬다. 구조 검사와 자연어 내용 검토를 구분하며 구조가 통과해도 사람의 검토가 필요하므로 종료 코드 2다. 실제 이메일·전화·외부 일정 변경은 수행하지 않는다.

2026-10-31 병렬 변경 중간의 합성 메모리 실모델 실행: 4개 대화의 구조 검사는 모두 통과했고 모델 호출은 순서대로 4·4·4·1회였다. 모호한 날짜 사례에서 모델은 날짜를 단정하지 않고 일정 식별 단서를 물었으나 날짜 자체를 직접 묻지는 않았다. 이 응답의 적합성은 사람의 검토가 필요하며, 이 결과는 최종 통합 상태나 실제 제공자 연결의 검증이 아니다.

## 공통 합성 입력

| 항목 | 입력 |
|---|---|
| 기준 시각 | 2026-11-01 09:00, `Asia/Seoul` |
| 고정 공동 약속 | 15:00~16:00 회의. 원본 시간과 버전을 기록한다. |
| 준비·이동 | 준비 15분, 이동 30분, 도착 여유 10분. 준비 14:05~14:20과 이동 14:20~14:50은 개인 일정으로 기록한다. |
| 유동 작업 | 미배치 공부 60분, 마감 20:30. 가능한 시간은 10:00~11:00 또는 16:30~17:30. |
| 명시 맥락 | 장기 선호는 오전 집중. 오늘은 피곤하므로 오전에 쉬고 오후에 공부하고 싶다는 일시 상황을 입력한다. |

## 시연 순서와 판정

1. **추천·검증.** “입력한 일정과 상황을 고려해 공부 시간을 추천해줘.” 오후 16:30~17:30 제안과 입력된 피로·고정 회의에 근거한 이유를 확인한다. 시간 충돌·마감·고정 일정 보호 검증이 통과해야 하며 관측하지 않은 수면/행동 이력을 만들어 내지 않아야 한다. 응답이 다르거나 정보가 부족하면 실제 결과를 기록한다.
2. **승인 전후.** 제안 상세에서 전후 내용과 버전을 확인한다. 승인 전에는 공부가 미배치이고 회의 원본이 유지돼야 한다. 개인 공부 제안만 승인하면 공부가 16:30~17:30에 반영되고 회의는 그대로다. 같은 승인 재전달은 첫 결과를 반환해야 한다. 거절·무응답 또는 승인 전 다른 일정 변경 후 오래된 제안은 반영하지 않는다.
3. **다음 행동(F09).** 가상 시각을 13:40으로 옮긴다. 14:05 준비가 다음 행동과 시각으로 표시되는지 확인한다. 사용자가 응답하지 않은 상태는 완료·미완료로 추정하지 않는다. 푸시 전달은 이 판정에 포함하지 않는다.
4. **영향 없는 지연(F10).** 가상 시각 13:40에서 “13:20에 돌아오려 했는데 20분 늦어 지금 도착했어. 14:05부터 준비할 수 있어.”라고 입력한다. 회의와 공부에 충돌이 없다면 재배치 제안 없이 기존 일정이 유지돼야 한다. 비교 범위는 입력 직전/직후의 일정 항목·시간과 일정 버전이다. 비교를 마친 뒤 가상 시각을 14:20으로 옮기고 준비를 직접 완료 처리해 그 항목의 체크인만 바뀌는지 확인한다.
5. **미완료 복구(F11).** 가상 시각을 17:40으로 옮기고 공부를 직접 미완료로 체크인한다. 체크인만으로 시간은 이동하지 않아야 한다. “공부는 여전히 필요하고 18:00~19:00에 할 수 있어. 마감은 20:30이야”라고 알려 준다. 18:00~19:00 등 충돌·마감을 통과한 대안을 제시하고 승인 전 기존 시간을 유지해야 한다. 사용자가 승인한 경우에만 해당 개인 작업을 반영한다. 기한이 지났거나 필요 여부가 불명확한 별도 사례는 확인 없이 재추천하지 않는다.

## 연락 및 외부 검증 경계

별도 합성 사례에서 공동 회의의 조정 대상을 명시적으로 선택하고 `recipient@example.test`로 연락 초안을 만든다. 초안은 `pending_approval`, 거절은 `rejected`, 내용·수신자·대안을 확인한 승인 후에는 `ready`다. 이 단계들은 실제 발송이나 회의 변경이 아니다. 메모리 모드에서는 Gmail 발송을 수행할 수 없다. `submitting`, `sent_or_connected`, `failed`, `outcome_unknown`은 별도의 격리된 모의 제공자/영속 저장소 검증에서 확인하며, 결과 불명은 자동 재발송하지 않는다.

2026-10-31 사용자 보고: 이메일 발송 작업·확인 완료. 후속 개발본에는 Gmail 회신 조회→저장된 발췌 사용자 확인→허용된 대안의 최신 검증·내부 일정 반영이 구현됐다. MAIN은 로컬 읽기 동의와 Gmail profile HTTP200·동일 계정을 확인했으며, 실제 회신 조회부터 일정 반영까지는 시연 전이다. 발송 접수는 상대 수락이 아니다. Twilio는 사용자 요청으로 보류한다. 시연 기록에는 실행 환경, 시각, 실제 결과, 성공/실패/미검증과 사용한 모의 여부만 남긴다.
