# PIKKU 아키텍처 결정 기록

작성: 2026-10-31 · 세진님/00 MAIN. [ARCHITECTURE](ARCHITECTURE.md)의 판단 근거를 기록한다. **사용자 확인**은 00 MAIN 대화에서 확인된 방향이며 팀 전체의 MVP 승인이나 구현 완료를 뜻하지 않는다. **개발 기준 채택**은 세진님의 문서 확정·개발 착수 요청에 따라 00이 정리한 v1 구현 기준이다. 팀 전체 검토 완료와 실제 연동 성공을 뜻하지 않는다. 제공자·호스팅 등 남은 선택은 미정으로 구분한다.

## 2026-10-31 실행 상태 보정

이 절은 최초 결정과 이후 실행 증거를 구분한다. 최신 작업 현황은 [구현 계획](IMPLEMENTATION_PLAN.md)의 첫 표를 따른다. 문서 채택과 실제 연결·배포 성공은 다르다.

- Terra/high의 실제 호출과 합성 일정의 PostgreSQL·예약·승인은 검증 기록이 있다. [모델 검증](MODEL_VERIFICATION.md). 아래 최초 검증 계획을 모델 비교 완료로 해석하지 않는다.
- 공개 테스트는 별도 배포 작업자의 인계 기준 Vercel 웹 + NAVER Cloud VM의 API/PostgreSQL/pg-boss + 임시 Cloudflare 터널이다. 정식 사용자 인증·고정 API 도메인·현재 개발본의 배포는 완료되지 않았다.
- 사용자는 Gmail 작업·확인을 **로컬 환경에서** 완료했다고 보고했다. 공개 테스트 계정의 Gmail 연결이나 상대 회신 처리까지 검증됐다는 의미는 아니다.
- Calendar 읽기·선택 가져오기 이후, 제한된 음성 대화·Gmail 회신 조회·사용자 확인·조건부 일정 반영을 ADR-009로 연결한다. 실제 Twilio 키 인증은 성공했지만 발신번호 조건·실통화는 미완료다. 연속 동기화·외부 일정 쓰기·자유 음성 협상은 포함하지 않는다.
- UI 전용 준비계획은 사용자 입력 시간을 서버 계산으로 제안하고 기존 승인 경로를 이용한다. 자유형 LLM 제안 전체에 준비·이동 관계를 강제하는 계약이 생긴 것은 아니다.

## ADR-001 — 모바일 방향과 화면

- **상태:** 개발 기준 채택. Expo + React Native + TypeScript, 채팅·월별·하루 세 화면.
- **결정 방향:** AI 채팅, 월별 캘린더, 하루 일정/To-do를 하나의 일정 데이터에 연결한다. 디자인은 팀의 와이어프레임을 따른다.
- **근거:** F02의 일정과 작업, F06·F07의 추천·승인, F09의 다음 행동을 모바일에서 이어서 제공한다. 사용자는 PWA보다 바로 모바일에서 사용할 React Native를 원했다.
- **대안/영향:** 웹/PWA 우선은 현재 사용자 방향과 맞지 않아 기준으로 삼지 않는다. Expo Go는 초기 확인 수단 후보이며 최종 설치 앱과 같지 않다. 네이티브 라이브러리·설정이 필요한 경우 개발 빌드를 검토한다. 개발 빌드 채택만으로 전화·이메일의 실제 자동 실행 권한이 확보되는 것은 아니다. [Expo 공식 설명](https://docs.expo.dev/develop/development-builds/introduction/)
- **남은 결정:** 실기기 우선 검증 대상과 서명·설치·시연 방법. 초기 개발은 Expo Go 호환 범위로 시작하고 네이티브 설정이 필요하면 development build를 사용한다. 양쪽 지원은 목표이며 성공 검증 전이다.

## ADR-002 — 한 S LLM의 대화와 코드 검증

- **상태:** 개발 기준 채택. 한 S LLM과 코드 검증을 분리한다.
- **결정 방향:** S LLM이 질문·조회·추천·설명을 판단하고 필요할 때 Tool을 호출한다. Schedule Engine은 계산·충돌·시간/고정 일정 제약을 코드로 검증한다. 실제 저장은 서버의 필수 검증 경로를 통과한다.
- **근거:** F03·F04·F06은 맥락에 대한 AI 판단, F05·F06·F07은 재현 가능한 계산과 반영 전 검증을 요구한다. “고마워”는 간단한 답변이면 충분하다.
- **대안/영향:** 모든 입력의 전체 재계획, 기본 분류용 별도 LLM, 프롬프트만으로 승인·충돌을 통제하는 방식은 권장하지 않는다. 같은 S LLM도 필요에 따라 여러 Tool 호출 단계를 거칠 수 있다.
- **예시:** “고마워” → 답변. “오늘 16:30 약속” → 대상과 시간을 확인하고 기존 공부와 충돌하면 대안을 제시. AI가 시간을 제안했어도 검증·승인 전에는 다른 일정을 옮기지 않는다.

## ADR-003 — 직접 저장과 AI 추가 변경의 승인 범위

- **상태:** 개발 기준 채택. 직접 저장과 추가 변경 승인을 분리하며 v1 오류/필드는 CONTRACTS를 따른다.
- **결정 방향:** 직접 입력 폼의 저장은 화면에 표시된 해당 변경의 확인으로 처리한다. AI가 추가로 바꾸려는 일정과 외부 행동은 별도 대상으로 승인받는다. 제안은 ID·버전·변경 목록에 승인을 묶고 최신 상태를 재검증한다.
- **근거:** F07의 선택권을 지키면서 같은 입력에 불필요한 이중 확인을 만들지 않는다. F06·F10의 충돌 대안과 오래된 제안 차단을 지원한다.
- **대안/영향:** 저장 한 번을 하루 전체 변경 승인으로 확대하지 않는다. 대화의 “고마워”, 침묵, 시간 트리거는 승인이 아니다. 변경안이 수정되면 그 내용을 다시 확인받는다.
- **예시:** 사용자가 새 약속을 저장하더라도 겹치는 공부의 자동 이동은 승인되지 않는다. 공부를 18시로 옮기는 안을 따로 선택하게 한다. 승인 대기 중 18시에 다른 약속이 생겼다면 이전 안을 적용하지 않는다.

## ADR-004 — 다중 캘린더의 동일성·출처 보존

- **상태:** 동일성·출처 원칙 채택. 첫 제공자 조회부터 연결하며 다중 제공자 전체 동기화는 후속 범위.
- **결정 방향:** 확인된 동일 이벤트는 앱에서 하나로 표시하고 원본 출처들을 유지한다. 제목·시간만으로 자동 병합하지 않는다. 불확실한 동일성과 원본 간 불일치는 확인 대상으로 남긴다.
- **근거:** F02·F12의 일정 조회·외부 권한 구분과 최신 통합 캘린더 요구. 한 일정의 중복 표시를 줄이되 별개 약속을 잃지 않아야 한다.
- **대안/영향:** 복제 이벤트의 출처 삭제, 반복 회차 통합, 아무 원본이나 최종값으로 선택하는 방식은 사용하지 않는다. 같은 요청 재시도의 중복 실행 차단은 별도 계약으로 둔다.
- **예시:** 동일 회의의 Google·다른 캘린더 출처를 연결한다. 한쪽 15시, 다른 쪽 16시면 시간 충돌을 표시하고 어느 값을 따를지 확인한다.

## ADR-005 — 단일 백엔드와 Agent 런타임

- **상태:** 개발 기준 채택. Node.js + TypeScript + Fastify, LangGraph JS. Hermes 설치·포크는 채택하지 않는다.
- **결정:** 하나의 백엔드에 책임을 나눈 모듈을 두고, 상태 흐름은 LangGraph JS로 구성한다. S LLM·Tool·Memory 경계는 Hermes 구조를 참고하되 Hermes 전체를 설치해 개조하는 것을 기본안으로 삼지 않는다.
- **근거:** F04·F06·F07의 추가 질문·Tool 호출·검증·승인 대기 상태를 명시하기 좋다. LangGraph는 LLM 단계와 결정적 코드를 함께 구성하며 LangChain의 고수준 Agent를 필수로 쓰지 않아도 된다. 패키지 내부 의존성까지 없다는 의미는 아니다. [LangGraph 공식 개요](https://docs.langchain.com/oss/javascript/langgraph/overview)
- **대안:** 직접 작성한 작은 상태 흐름은 의존성이 적지만 상태 전환·재개를 직접 관리해야 한다. Hermes 통합은 기존 Agent 기능 재사용 가능성이 있으나 앱별 사용자·승인·일정 계약에 맞춘 검증이 필요하다. 두 런타임을 동시에 결합할 이득은 아직 확인되지 않았다. 이는 본 프로젝트에 대한 설계 판단이다. [Hermes 공식 구조](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)
- **영향:** LangGraph의 중단·재개를 사용해도 승인된 변경의 최신성·중복 실행을 자동 보장하지 않는다. 지속 저장 설정과 실행 로직이 필요하다. 복구 시 재실행되는 코드의 외부 효과도 별도 관리한다. [LangGraph 중단·재개](https://docs.langchain.com/oss/javascript/langgraph/interrupts)
- **남은 결정:** 호스팅·프로젝트 API 접근 검증. Fastify는 모바일과 같은 TypeScript로 요청/계약을 검증하는 작은 HTTP 서버를 구성하기 위해 선택했다. 패키지 버전은 설치 시 검증·잠금하며 코드를 채택했다는 사실과 실행 성공을 구별한다. [Fastify 공식 문서](https://fastify.dev/docs/latest/)

## ADR-006 — Memory와 서버 Scheduler

- **상태:** 개발 기준 채택. PostgreSQL + pg-boss 서버 Scheduler. 공개 테스트는 VM PostgreSQL 사용 인계, Supabase 필수 아님.
- **결정:** 확정 일정, 제안/승인, Memory, Agent 진행 상태를 논리적으로 구분한다. 같은 DB에 저장할 수 있으며 별도 서비스/DB를 각각 만들 필요는 없다. Scheduler는 서버에서 검토 이벤트를 만들고 같은 S LLM 흐름을 호출한다.
- **근거:** F03은 선호·관측·추정 구분을, F06·F09는 시간에 따른 추천과 행동 안내를 요구한다. 사용자 기기의 화면 상태와 추천 실행 시점을 분리하고 시간 이벤트에도 같은 승인 규칙을 적용한다.
- **대안/영향:** 모든 대화를 영구 선호로 저장하거나 모든 주기 확인마다 LLM을 호출하지 않는다. 재시작 복구는 안정성 과제로 두며 제품 범위를 늘리는 조건으로 삼지 않는다.
- **예시:** 전날 승인한 공부 계획을 아침에 검토했지만 새 제약이 없으면 유지한다. “오늘 오전은 쉬고 싶어”라는 새 입력이 있으면 가능한 오후 대안을 제안한다.
- **남은 결정:** 정식 운영·보존 기간·실제 푸시 전달. 로컬 접속 및 별도 공개 테스트의 VM 저장은 검증 기록/인계를 따른다. 전날·아침 서버 트리거는 v1 시연 목표에 포함하고 시각은 사용자 설정으로 둔다. 설정 미입력 시 disabled, 60분 초과 밀린 예약은 skipped로 두는 초기 정책은 CONTRACTS §5에 정했다.
- **선택 이유/대안:** PostgreSQL은 일정 버전·승인·중복 기록을 트랜잭션으로 묶을 수 있고 pg-boss가 같은 DB를 재사용하므로 별도 Redis를 추가하지 않는다. Supabase는 호스팅 후보일 뿐 필수 의존성이 아니다. Hermes 내장 Cron은 Hermes 운영을, LangSmith Cron은 별도 배포 조건을 요구한다. [비교와 근거](ARCHITECTURE.md). pg-boss 도입만으로 외부 발송 중복 방지가 완성되는 것은 아니다.

## ADR-007 — 개발·비교 기준 모델

- **상태:** 2026-10-31 사용자 지정. 실제 호출은 검증됐으며 모델 간 비교는 미실행.
- **결정:** 최초 추천이었던 `gpt-6.1-sol` 대신 **`gpt-6.1-terra` + `reasoning.effort: high`**를 개발·비교 기준으로 사용한다. `high`는 모델 이름의 일부가 아니라 추론 설정이다. S LLM의 Tool Calling은 Responses API를 사용한다. [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-terra)
- **이유:** 사용자가 실제 테스트 비교를 전제로 기준 모델을 지정했다. Terra의 추천 품질이나 지연시간이 다른 모델보다 낫다는 실측 근거는 아직 없다.
- **검증 계획:** 같은 일정·대화·프롬프트·Tool·시간대 조건에서 단순 답변, 맥락에 따른 대안, 누락 질문, 영향 없음, 오래된 승인 사례를 비교한다. 실제 모델/추론 설정, 결과 품질, 응답시간, 사용량을 기록한다. 비교 모델과 설정은 평가 전에 명시하며 자동 모델 대체나 추론 수준 변경을 기본 동작으로 넣지 않는다.
- **검증 경계:** 프로젝트 키의 호출과 요청·응답 모델 설정은 [모델 검증](MODEL_VERIFICATION.md)에 기록했다. 호출 한도, 대표 품질·지연·비용 및 다른 모델과의 비교는 미검증이다. 개별 사례의 성공을 전반 품질 평가 완료로 확대하지 않는다.

## ADR-008 — 일정 변경의 실제 전화·이메일 대행

- **상태:** 2026-10-31 사용자 핵심 요구 확인. 상세 승인·상태 흐름은 v1 개발 기준 채택. 제공자와 채널별 실제 시연 가능성은 병렬 검증 중.
- **요구:** 오늘 저녁 친구와의 약속을 내일 또는 모레로 옮기는 추천을 사용자가 승인하면 AI가 사용자를 대신해 상대에게 실제 전화 또는 이메일로 요청한다. 전화/메일 앱을 여는 것만으로 요구를 충족했다고 하지 않는다. 기존 PRD F12의 연락대행을 일괄적인 나중 확장으로 취급하지 않는다.
- **결정 흐름:** 추천 → 대상·채널·내용·허용 대안 승인 → 연락 실행 → 응답 대기/수락/거절/다른 대안 구분 → 최신 상태 재검증 → 합의된 일정 반영. 발송 완료·통화 종료는 약속 변경 합의가 아니다. 상대 수락 전 원래 약속은 보존한다.
- **제공자 순서:** 사용자가 Gmail 우선 연결을 선택했다. 로컬 개발 사용자용 Gmail 발송/OAuth 경로부터 구현하며 실제 계정 동의·발송은 별도 검증한다. Google Calendar와 Twilio 실제 발신은 후속 검토다. 전화는 별도 음성 처리 계층이 필요하며 일정 판단 모델인 Terra/high를 임의로 교체하지 않는다. 근거와 검증 조건은 [아키텍처 §7](ARCHITECTURE.md)에 기록한다.
- **다음 판단:** 세진님·서연님은 실제 연결 가능성, 영휘님은 승인 범위 안의 대화·예외, 찬욱님은 연락 작업/응답/일정 버전 저장, PM은 연락 요청·대기·실패·변경 완료 UX와 시연 범위를 맞춘다. 전화가 미검증이면 미검증으로 보고하며 메일이나 모의 통화로 완료를 대체하지 않는다.

## ADR-009 — 제한된 음성 대화와 검증된 회신의 조건부 적용

- **상태:** 2026-10-31 사용자가 양방향 AI 대화·회신 확인·최종 일정 반영 구현을 요청했다. 아래 설계로 증분 개발하며 실통화 성공은 별도 검증한다.
- **결정:** Twilio `Gather`의 한국어 음성 입력과 `Say`를 사용한 턴 단위 대화로 시작한다. 승인된 연락 내용과 시간 대안만 `gpt-6.1-terra/high`에 제공한다. 모델은 대화를 해석하고 질문하지만, 일정 변경이나 상대 수락 증거를 직접 생성하지 않는다. 선택 대안을 다시 읽고 명시적 번호 입력으로 확인한 뒤 서버가 검증한다.
- **이유:** F12의 실제 연락·합의와 F07의 승인 범위를 유지하면서 기존 텍스트 모델·PostgreSQL을 재사용한다. 별도 실시간 음성 모델·WebSocket 서비스를 추가하지 않는다. 끊김 없는 동시 음성 대화와는 다르며 모델 지연·무응답은 제한 시간과 번호 선택 안내로 처리한다. [Gather](https://www.twilio.com/docs/voice/twiml/gather)
- **증거 경계:** 전화는 서명·계정·CallSid·발신/수신번호·세션·단계가 연결된 콜백만 처리한다. Gmail은 별도 읽기 동의로 실제 전송 메시지·스레드·회신 연관을 확인하되 헤더 일치만으로 상대 신원을 인증했다고 하지 않는다. 불확실한 이메일 회신은 화면에 실제 답변을 보여주고 사용자의 명시 확인을 거친다.
- **반영:** 저장된 회신과 승인한 대안, 최신 일정·맥락·수신자·유효기간을 같은 트랜잭션에서 검증한다. 중복 콜백은 재적용하지 않으며 새 충돌·만료·범위 밖 대안은 검토 필요로 남긴다. 반영 대상은 삐꾸 내부 일정이며 Google 원본 쓰기를 의미하지 않는다.
- **실행 조건:** 영속 DB, 안전한 사용자별 Twilio 자격 저장, 고정된 공개 HTTPS 웹훅 주소와 서버 세션 키가 필요하다. 양방향 설정이 없으면 발신을 거절하며 단방향 성공으로 대체하지 않는다. 현재 Trial의 Gather/Say 지원 표만으로 계정별 커스텀 발신 성공을 단정하지 않는다. [Twilio 보안](https://www.twilio.com/docs/usage/security) · [Trial 제약](https://www.twilio.com/docs/usage/trials/try-out-voice)

2026-10-31 세진님 요청에 따라 핵심 기술/최소 계약을 먼저 공유하고 구현과 제공자 검증을 병렬 진행한다. 미정 제공자가 전체 개발 착수를 막지 않는다. 문서는 최신 main과 비교한 PR로 공유하고 병합은 별도로 결정한다. 계약 변경은 영향받는 담당자에게 알리고 해당 ADR·CONTRACTS를 함께 갱신한다.

실제 시연 목표는 PRD §2의 v1 표를 따른다. 전화·메일 전체 완료, 실기기 양쪽 지원, DB 복구, 모델 호출 성공은 별도의 실측 증거가 필요하다.


## ADR-010 — 장소별 날씨·역 도착 정보와 공개 연결 경계

- **결정/근거:** 사용자 요청으로 Open-Meteo 시간별 예보와 서울 역 도착 정보를 준비계획의 선택적 참고 패널로 연결한다. 교통수단은 사용자가 고르며, 현재 역 도착값을 전체 여정 ETA나 약속 시각 교통 예측으로 대체하지 않는다. 누락/실패/만료는 별도 상태다.
- **연결:** 서버 읽기 전용 어댑터·인증 API를 사용하고 수동 입력·기존 승인 경계를 유지한다. 5분 예보/15초 도착 캐시와 단조시계 기반 화면 만료를 적용한다. 필드·오류·한도는 CONTRACTS §12가 정본이다.
- **제약:** 무료 날씨 이용/출처 조건을 지킨다. 서울 HTTPS는 현재 환경 timeout으로 미검증이며 명시 HTTP 실키 연결만 성공했다. 키·역명 평문 상류 위험을 기록하고 자동 다운그레이드는 금지한다.
- **공개 계정:** 시연용 서버 Google 연결은 정확히 한 등록 멤버에만 바인딩하며 나머지 멤버에게 공유하지 않는다. 정식 사용자별 OAuth 가입은 후속 과제다.
- **배포:** contactResponses/voiceSessions JSONB를 공유하는 두 API/예약 프로세스를 함께 새 버전으로 전환한다. 일관된 사전 DB 백업과 격리 복원 검증을 거치며, 새 필드 저장 뒤 이전 코드만 재기동하는 롤백은 금지한다.

## ADR-011 — ClawOps 전화 제공자 전환

- **결정:** 2026-11-01 사용자 요청으로 신규 전화 연결의 기본 제공자를 ClawOps로 바꾼다. 기존 Twilio 설정·경로를 보존하고 불변 연락 승인·최신성·영속 실행 기록·중복 차단은 재사용한다. 키가 설정됐다는 이유로 발신하거나 모든 사용자에게 같은 계정을 공유하지 않는다.
- **최소 경로:** 기존 전화 상태기계와 호환되는 VoiceML HTTP/XML을 사용한다. 계정 소유 번호 조회, 사용자별 비밀 저장, 승인된 대안 안내·키패드 선택·최종 재확인, 원본 콜백 HMAC-SHA256 검증과 통화/연락 결합을 구현한다. 제공자 API 접수와 상대 수락을 구분한다.
- **이유/제한:** [VoiceML 공식 문서](https://platform.claw-ops.com/docs/build/voiceml)의 Gather는 DTMF만 지원한다. 따라서 Twilio의 speech 속성을 그대로 이식하지 않는다. [서명키](https://platform.claw-ops.com/docs/webhooks/signature-verification)는 API 키와 별도로 준비한다. 설정·모의 테스트·실제 발신 및 일정 반영 검증은 각각 기록한다.
- **후속 결정:** 이 VoiceML 증분 다음의 자유 음성 대화는 ADR-012를 따른다. Managed Agent와 VoiceML Url은 한 발신에서 동시에 지정할 수 없으며, 전사·LLM 판단이나 임의 숫자 이벤트만으로 자동 수락·일정 반영을 허용하지 않는다. 전화 제공자 선택은 메인 S LLM을 교체하지 않는다.

## ADR-012 — 관리형 양방향 음성과 사용자 최종 확인

- **결정:** 2026-11-01 사용자가 자유로운 한국어 음성 대화 구현을 요청했다. ClawOps Managed Agent와 통화별 CallContext를 사용하고 우리 서버에 별도 음성 WebSocket 런타임은 추가하지 않는다. 기존 VoiceML·Twilio 모드를 보존하며 신규 ClawOps 화면은 관리형 음성을 기본으로 한다.
- **연결:** 계정 소유 번호·agent ID를 확인하고 사용자별 비밀 파일에 계정/API 키를 저장한다. 승인된 연락 설명·대안만 통화별 전달하며 개인 Memory·전체 일정이나 앱의 쓰기 Tool은 제공하지 않는다. 앱의 메인 모델은 Terra/high를 유지한다. 테스트 전용 agent의 실제 설정 조회에서 `gpt-realtime-2.1-mini`, 한국어, 120초 제한과 확정 전사 이벤트를 확인했다.
- **회신:** 계정 Bearer 인증으로 서버가 통화·전사 목록을 조회한다. 발신 당시의 연락·계정·agent·발신번호를 기존 영속 실행 상태에 결합하고 제공자 통화 ID·수신번호·방향·생성시각과 대조한다. 우리 서버가 웹훅을 수신하지 않는 이 경로에는 Webhook Signing Secret이 필요하지 않다. VoiceML의 서명 검증은 유지한다.
- **승인:** 통화 완료·정상 이벤트 종료·전체 페이지·상대 발화·전체 전사 상한을 확인해도 응답은 `unclear`다. 앱 사용자가 전체 전사를 읽고 허용 대안을 명시적으로 재승인한 뒤 기존 승인 스냅샷·일정 최신성·충돌·중복 검증으로 반영한다. 미완료·무음·부분 전사·잘림은 재승인 대상으로 저장하지 않는다. AI의 발화·추측·키패드 이벤트만으로 확정하지 않는다.
- **대화·종료 보완:** 실제 통화에서 내부 지침 설명과 종료 지연이 발견됐다. 첫 인사 외 메타 지침 낭독을 금지하고, 다시 말해 달라는 요청에는 업무 요점만 반복한다. 관리형 서울 일정은 같은 해의 연도·한국 표준시·UTC 시차를 생략하되 날짜 변경·다른 해·비서울/DST 표현은 보존한다. 종료 도구를 명시적으로 허용하며 서버 감시가 본인 통화의 확정된 상대 발화에서 명확한 종료 요청을 확인하면 종료 API를 한 번 시도한다. 부정·인용·AI 발화로 종료하지 않는다.
- **종료 한계:** 감시는 프로세스 로컬이며 3초 간격, 통화 중 상태 관측 후 120초 또는 감시 시작 150초를 한도로 한다. 종료 시도 중복 방지는 같은 프로세스 수명 내에 한정한다. 계정·번호·통화를 제공자 조회로 확인하지 못했거나 자격/연락이 바뀌면 종료하지 않으며, 재시작 뒤 감시 재개를 보장하지 않는다. 제공자 전용 agent의 120초 제한은 별도다. 수정 후 추가 실통화는 사용자가 요청하지 않아 모의 검증만 진행했다.
- **한계:** 프롬프트는 승인 범위 밖의 대안을 확정하지 않도록 안내하지만 발화 자체의 완전한 준수를 보장하지 않는다. 그래서 쓰기는 서버와 사용자 승인에 남긴다. 기존 VoiceML의 실통화 검증과 관리형 음성의 실제 연결·청취·대화 품질은 서로 다른 증거로 기록한다.
- **근거:** [관리형 음성·이벤트](https://platform.claw-ops.com/docs/voice-agent/managed), [통화별 CallContext](https://docs.claw-ops.com/api-reference/claw-ops-api/calls/create-call), [전사 목록](https://platform.claw-ops.com/docs/api/calls/listCallLiveEvents).

## ADR-013 — 워치 건강 데이터의 선택적 로컬 읽기

- **상태/범위:** 2026-11-01 사용자가 준비 문서 기반 병렬 구현을 요청했다. 첫 단계는 iPhone HealthKit·Android Health Connect의 최근 7일 걸음 수·운동 기록 읽기와 설정 화면이다. 실기기 동의·조회는 미검증이다.
- **결정/이유:** 기존 Expo/RN 앱에 플랫폼별 지연 로딩 어댑터와 공통 집계를 넣는다. 서버·DB·메인 Agent를 바꾸지 않고 기기 메모리에서 연결 가능성과 표시 의미부터 확인한다. 별도 Watch 앱·직접 통신·전체 건강 항목 수집은 이 단계에 필요하지 않다.
- **권한/의미:** 항목을 직접 선택하고 버튼을 누른 뒤 읽기만 요청한다. 빈 값과 관측 0, iOS 권한 불명확을 구분한다. 운동시간은 일시정지 포함 기록 구간이며 실제 활동 시간이 아니다. 출처/표본/5분 만료 신호를 사용하고 건강 상태·장기 선호를 추정하지 않는다.
- **영향:** Expo Go/웹은 미지원 안내를 제공하며 네이티브 개발 빌드가 필요하다. 앱 Android 최소 API를 24→26으로 올렸고 건강 연결은 API 28 이상이다. 개발용 앱 ID·읽기 권한만 설정했다. iPhone은 무료 Personal Team으로 테스트 가능하나 실제 서명/설치는 별도다.
- **다음 경계:** 건강 원본·요약을 서버/LLM/연락에 전송하지 않는다. 이후 AI 활용은 별도 동의·최소 전송·보관/삭제 계약을 먼저 합의한다. [구현·설치·검증 기록](WEARABLE_INTEGRATION.md) · [로컬 계약 §15](CONTRACTS.md#15-건강-데이터-로컬-전용-계약)

## ADR-014 — 회원·반복 루틴·Calendar 쓰기 증분

- **상태:** 2026-11-01 사용자가 세 기능의 실제 병렬 구현을 요청했다. 기존 main/전화 인계 브랜치와 분리한 기능 브랜치에서 구현하며 실제 Google 동의·원본 변경·공개 배포는 별도다.
- **회원:** 기존 Google 클라이언트/redirect와 공식 ID token 검증을 재사용해 가입·로그인, sub 기반 회원, 해시 세션과 로그아웃을 구현한다. 앱 인증과 Calendar/Gmail 연결 권한은 분리하고 preview 자료를 새 회원에게 자동 귀속하지 않는다.
- **루틴:** 요일·현지시각·IANA 시간대 규칙과 최대 31일의 수동 회차 생성을 채택한다. 기존 생성 회차를 보존하고 수정/비활성은 이후 미생성 회차에 적용한다. 기존 일정 command/checkin·충돌 검증을 재사용한다.
- **동기화:** 선택 캘린더·선택 개인 이벤트의 수동 양방향 동기화를 구현한다. 삭제는 opt-in과 삭제 이력/ETag 검증을 모두 요구하고 공유 일정 승인 경계를 유지한다. 자동 webhook과 무기한 반복/전체 Calendar 일반화는 포함하지 않는다.
- **저장:** PostgreSQL을 유지하고 보조 테이블을 추가한다. `atomicWithClient`로 일정과 회차/매핑을 같은 트랜잭션에 묶는다. 외부 쓰기 결과 불명은 재전송 없이 검토로 남긴다. 삭제 이력 필드 추가 후 구 strict decoder로의 코드 단독 롤백은 금지한다.
- **근거/계약:** [사용 방법·한계](MEMBER_ROUTINE_CALENDAR.md), [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect), [Calendar sync](https://developers.google.com/workspace/calendar/api/guides/sync), [조건부 쓰기](https://developers.google.com/workspace/calendar/api/guides/version-resources).

2026-11-01 디자인 접합 전 보완: 기존 sync 연결의 추가 내보내기 선택과, 저장된 연락 합의 적용·정확한 원본/현재 일정·주최 계정/Calendar owner를 검증한 기존 공동 약속의 시간 반영을 연결한다. 새 공동 생성/삭제와 미확인 합의는 허용하지 않는다. 실제 PostgreSQL/HTTP 종단에서 발견한 sync 자기 잠금을 피하기 위해 전체 외부 실행을 멱등 실행기의 바깥 트랜잭션으로 감싸지 않고 자체 영속 효과 ledger를 사용한다. lease 만료 자동 재실행 금지는 유지한다.
