# PIKKU 아키텍처 결정 기록

작성: 2026-10-31 · 세진님/00 MAIN. [ARCHITECTURE](ARCHITECTURE.md)의 판단 근거를 기록한다. **사용자 확인**은 00 MAIN 대화에서 확인된 방향이며 팀 전체의 MVP 승인이나 구현 완료를 뜻하지 않는다. **개발 기준 채택**은 세진님의 문서 확정·개발 착수 요청에 따라 00이 정리한 v1 구현 기준이다. 팀 전체 검토 완료와 실제 연동 성공을 뜻하지 않는다. 제공자·호스팅 등 남은 선택은 미정으로 구분한다.

## ADR-001 — 모바일 방향과 화면

- **상태:** 개발 기준 채택. Expo + React Native + TypeScript, 채팅·월별·하루 세 화면.
- **결정 방향:** AI 채팅, 월별 캘린더, 하루 일정/To-do를 하나의 일정 데이터에 연결한다. 디자인은 팀의 와이어프레임을 따른다.
- **근거:** F02의 일정과 작업, F06·F07의 추천·승인, F09의 다음 행동을 모바일에서 이어서 제공한다. 사용자는 PWA보다 바로 모바일에서 사용할 React Native를 원했다.
- **대안/영향:** 웹/PWA 우선은 현재 사용자 방향과 맞지 않아 기준으로 삼지 않는다. Expo Go는 초기 확인 수단 후보이며 최종 설치 앱과 같지 않다. 네이티브 라이브러리·설정이 필요한 경우 개발 빌드를 검토한다. 개발 빌드 채택만으로 전화·이메일의 실제 자동 실행 권한이 확보되는 것은 아니다. [Expo 공식 설명](https://docs.expo.dev/develop/development-builds/introduction/)
- **남은 결정:** 실기기 우선 검증 대상과 서명·설치·시연 방법. 초기 개발은 Expo Go 호환 범위로 시작하고 네이티브 설정이 필요하면 development build를 사용한다. 양쪽 지원은 목표이며 성공 검증 전이다.

## ADR-002 — 한 S LLM의 대화와 코드 검증

- **상태:** 개발 기준 채택. 한 S LLM과 코드 검증을 분리한다.
- **결정 방향:** S LLM이 질문·조회·추천·설명을 판단하고 필요할 때 Tool을 호출한다. Schedule Engine은 계산·충돌·시간/고정 일정 제약을 코드로 검증한다. 실제 저장은 서버의 필수 검증 경로를 통과한다.
- **근거:** F03·F04·F06은 맥락에 대한 AI 판단, F05·F06·F07은 재현 가능한 계산과 반영 전 검증을 요구한다. “고마워”는 간단한 답변이면 충분하다.
- **대안/영향:** 모든 입력의 전체 재계획, 기본 분류용 별도 LLM, 프롬프트만으로 승인·충돌을 통제하는 방식은 권장하지 않는다. 같은 S LLM도 필요에 따라 여러 Tool 호출 단계를 거칠 수 있다.
- **예시:** “고마워” → 답변. “오늘 16:30 약속” → 대상과 시간을 확인하고 기존 공부와 충돌하면 대안을 제시. AI가 시간을 제안했어도 검증·승인 전에는 다른 일정을 옮기지 않는다.

## ADR-003 — 직접 저장과 AI 추가 변경의 승인 범위

- **상태:** 개발 기준 채택. 직접 저장과 추가 변경 승인을 분리하며 v1 오류/필드는 CONTRACTS를 따른다.
- **결정 방향:** 직접 입력 폼의 저장은 화면에 표시된 해당 변경의 확인으로 처리한다. AI가 추가로 바꾸려는 일정과 외부 행동은 별도 대상으로 승인받는다. 제안은 ID·버전·변경 목록에 승인을 묶고 최신 상태를 재검증한다.
- **근거:** F07의 선택권을 지키면서 같은 입력에 불필요한 이중 확인을 만들지 않는다. F06·F10의 충돌 대안과 오래된 제안 차단을 지원한다.
- **대안/영향:** 저장 한 번을 하루 전체 변경 승인으로 확대하지 않는다. 대화의 “고마워”, 침묵, 시간 트리거는 승인이 아니다. 변경안이 수정되면 그 내용을 다시 확인받는다.
- **예시:** 사용자가 새 약속을 저장하더라도 겹치는 공부의 자동 이동은 승인되지 않는다. 공부를 18시로 옮기는 안을 따로 선택하게 한다. 승인 대기 중 18시에 다른 약속이 생겼다면 이전 안을 적용하지 않는다.

## ADR-004 — 다중 캘린더의 동일성·출처 보존

- **상태:** 동일성·출처 원칙 채택. 첫 제공자 조회부터 연결하며 다중 제공자 전체 동기화는 후속 범위.
- **결정 방향:** 확인된 동일 이벤트는 앱에서 하나로 표시하고 원본 출처들을 유지한다. 제목·시간만으로 자동 병합하지 않는다. 불확실한 동일성과 원본 간 불일치는 확인 대상으로 남긴다.
- **근거:** F02·F12의 일정 조회·외부 권한 구분과 최신 통합 캘린더 요구. 한 일정의 중복 표시를 줄이되 별개 약속을 잃지 않아야 한다.
- **대안/영향:** 복제 이벤트의 출처 삭제, 반복 회차 통합, 아무 원본이나 최종값으로 선택하는 방식은 사용하지 않는다. 같은 요청 재시도의 중복 실행 차단은 별도 계약으로 둔다.
- **예시:** 동일 회의의 Google·다른 캘린더 출처를 연결한다. 한쪽 15시, 다른 쪽 16시면 시간 충돌을 표시하고 어느 값을 따를지 확인한다.

## ADR-005 — 단일 백엔드와 Agent 런타임

- **상태:** 개발 기준 채택. Node.js + TypeScript + Fastify, LangGraph JS. Hermes 설치·포크는 채택하지 않는다.
- **결정:** 하나의 백엔드에 책임을 나눈 모듈을 두고, 상태 흐름은 LangGraph JS로 구성한다. S LLM·Tool·Memory 경계는 Hermes 구조를 참고하되 Hermes 전체를 설치해 개조하는 것을 기본안으로 삼지 않는다.
- **근거:** F04·F06·F07의 추가 질문·Tool 호출·검증·승인 대기 상태를 명시하기 좋다. LangGraph는 LLM 단계와 결정적 코드를 함께 구성하며 LangChain의 고수준 Agent를 필수로 쓰지 않아도 된다. 패키지 내부 의존성까지 없다는 의미는 아니다. [LangGraph 공식 개요](https://docs.langchain.com/oss/javascript/langgraph/overview)
- **대안:** 직접 작성한 작은 상태 흐름은 의존성이 적지만 상태 전환·재개를 직접 관리해야 한다. Hermes 통합은 기존 Agent 기능 재사용 가능성이 있으나 앱별 사용자·승인·일정 계약에 맞춘 검증이 필요하다. 두 런타임을 동시에 결합할 이득은 아직 확인되지 않았다. 이는 본 프로젝트에 대한 설계 판단이다. [Hermes 공식 구조](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)
- **영향:** LangGraph의 중단·재개를 사용해도 승인된 변경의 최신성·중복 실행을 자동 보장하지 않는다. 지속 저장 설정과 실행 로직이 필요하다. 복구 시 재실행되는 코드의 외부 효과도 별도 관리한다. [LangGraph 중단·재개](https://docs.langchain.com/oss/javascript/langgraph/interrupts)
- **남은 결정:** 호스팅·프로젝트 API 접근 검증. Fastify는 모바일과 같은 TypeScript로 요청/계약을 검증하는 작은 HTTP 서버를 구성하기 위해 선택했다. 패키지 버전은 설치 시 검증·잠금하며 코드를 채택했다는 사실과 실행 성공을 구별한다. [Fastify 공식 문서](https://fastify.dev/docs/latest/)

## ADR-006 — Memory와 서버 Scheduler

- **상태:** 개발 기준 채택. PostgreSQL + pg-boss 서버 Scheduler. 호스팅은 미정, Supabase 필수 아님.
- **결정:** 확정 일정, 제안/승인, Memory, Agent 진행 상태를 논리적으로 구분한다. 같은 DB에 저장할 수 있으며 별도 서비스/DB를 각각 만들 필요는 없다. Scheduler는 서버에서 검토 이벤트를 만들고 같은 S LLM 흐름을 호출한다.
- **근거:** F03은 선호·관측·추정 구분을, F06·F09는 시간에 따른 추천과 행동 안내를 요구한다. 사용자 기기의 화면 상태와 추천 실행 시점을 분리하고 시간 이벤트에도 같은 승인 규칙을 적용한다.
- **대안/영향:** 모든 대화를 영구 선호로 저장하거나 모든 주기 확인마다 LLM을 호출하지 않는다. 재시작 복구는 안정성 과제로 두며 제품 범위를 늘리는 조건으로 삼지 않는다.
- **예시:** 전날 승인한 공부 계획을 아침에 검토했지만 새 제약이 없으면 유지한다. “오늘 오전은 쉬고 싶어”라는 새 입력이 있으면 가능한 오후 대안을 제안한다.
- **남은 결정:** PostgreSQL 호스팅/접속, 보존 기간, 실제 푸시 전달. 전날·아침 서버 트리거는 v1 시연 목표에 포함하고 시각은 사용자 설정으로 둔다. 설정 미입력 시 disabled, 60분 초과 밀린 예약은 skipped로 두는 초기 정책은 CONTRACTS §5에 정했다.
- **선택 이유/대안:** PostgreSQL은 일정 버전·승인·중복 기록을 트랜잭션으로 묶을 수 있고 pg-boss가 같은 DB를 재사용하므로 별도 Redis를 추가하지 않는다. Supabase는 호스팅 후보일 뿐 필수 의존성이 아니다. Hermes 내장 Cron은 Hermes 운영을, LangSmith Cron은 별도 배포 조건을 요구한다. [비교와 근거](ARCHITECTURE.md). pg-boss 도입만으로 외부 발송 중복 방지가 완성되는 것은 아니다.

## ADR-007 — 개발·비교 기준 모델

- **상태:** 2026-10-31 사용자 지정. 실제 호출·비교는 미실행.
- **결정:** 최초 추천이었던 `gpt-6.1-sol` 대신 **`gpt-6.1-terra` + `reasoning.effort: high`**를 개발·비교 기준으로 사용한다. `high`는 모델 이름의 일부가 아니라 추론 설정이다. S LLM의 Tool Calling은 Responses API를 사용한다. [공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-terra)
- **이유:** 사용자가 실제 테스트 비교를 전제로 기준 모델을 지정했다. Terra의 추천 품질이나 지연시간이 다른 모델보다 낫다는 실측 근거는 아직 없다.
- **검증 계획:** 같은 일정·대화·프롬프트·Tool·시간대 조건에서 단순 답변, 맥락에 따른 대안, 누락 질문, 영향 없음, 오래된 승인 사례를 비교한다. 실제 모델/추론 설정, 결과 품질, 응답시간, 사용량을 기록한다. 비교 모델과 설정은 평가 전에 명시하며 자동 모델 대체나 추론 수준 변경을 기본 동작으로 넣지 않는다.
- **미검증:** 팀 API의 해당 모델 접근권한·호출 한도, SDK/어댑터의 설정 전달, 실제 지연·비용. 문서상의 지원과 프로젝트에서의 호출 성공은 구분한다. 모델 설정을 문서에 반영한 것이 코드 연결이나 평가 완료를 뜻하지 않는다.

## ADR-008 — 일정 변경의 실제 전화·이메일 대행

- **상태:** 2026-10-31 사용자 핵심 요구 확인. 상세 승인·상태 흐름은 v1 개발 기준 채택. 제공자와 채널별 실제 시연 가능성은 병렬 검증 중.
- **요구:** 오늘 저녁 친구와의 약속을 내일 또는 모레로 옮기는 추천을 사용자가 승인하면 AI가 사용자를 대신해 상대에게 실제 전화 또는 이메일로 요청한다. 전화/메일 앱을 여는 것만으로 요구를 충족했다고 하지 않는다. 기존 PRD F12의 연락대행을 일괄적인 나중 확장으로 취급하지 않는다.
- **결정 흐름:** 추천 → 대상·채널·내용·허용 대안 승인 → 연락 실행 → 응답 대기/수락/거절/다른 대안 구분 → 최신 상태 재검증 → 합의된 일정 반영. 발송 완료·통화 종료는 약속 변경 합의가 아니다. 상대 수락 전 원래 약속은 보존한다.
- **제공자 순서:** 사용자가 Gmail 우선 연결을 선택했다. 로컬 개발 사용자용 Gmail 발송/OAuth 경로부터 구현하며 실제 계정 동의·발송은 별도 검증한다. Google Calendar와 Twilio 실제 발신은 후속 검토다. 전화는 별도 음성 처리 계층이 필요하며 일정 판단 모델인 Terra/high를 임의로 교체하지 않는다. 근거와 검증 조건은 [아키텍처 §7](ARCHITECTURE.md)에 기록한다.
- **다음 판단:** 세진님·서연님은 실제 연결 가능성, 영휘님은 승인 범위 안의 대화·예외, 찬욱님은 연락 작업/응답/일정 버전 저장, PM은 연락 요청·대기·실패·변경 완료 UX와 시연 범위를 맞춘다. 전화가 미검증이면 미검증으로 보고하며 메일이나 모의 통화로 완료를 대체하지 않는다.

## v1 적용과 변경

2026-10-31 세진님 요청에 따라 핵심 기술/최소 계약을 먼저 공유하고 구현과 제공자 검증을 병렬 진행한다. 미정 제공자가 전체 개발 착수를 막지 않는다. 문서는 최신 main과 비교한 PR로 공유하고 병합은 별도로 결정한다. 계약 변경은 영향받는 담당자에게 알리고 해당 ADR·CONTRACTS를 함께 갱신한다.

실제 시연 목표는 PRD §2의 v1 표를 따른다. 전화·메일 전체 완료, 실기기 양쪽 지원, DB 복구, 모델 호출 성공은 별도의 실측 증거가 필요하다.
