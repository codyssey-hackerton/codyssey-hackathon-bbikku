# 디자인 결합용 기능 연결표

2026-11-01. 현재 구현과 디자인의 연결 및 검증 경계다. 최신 증분은 바로 아래에 기록하고, 이후의 이전 계획과 검증 기록은 당시 상태로 보존한다. 임의로 디자인 화면을 추정해 추가하지 않는다.

## 채팅 안 제안 선택·승인과 간결한 요약 — 2026-11-01 최신 증분

사용자 확정 요구에 따라 새 AI 제안은 해당 답변 아래의 작은 카드에 제목·현지 시간·수락/수정/거절을 바로 표시한다. 채팅에서는 긴 제안 상세를 펼치지 않으며, 짧은 추천 이유만 선택적으로 확인한다. 제안 목록도 이유 전문 대신 일정 제목을 사용하며 여러 항목은 첫 제목과 추가 개수로 요약한다. 새 일정은 추가할 내용만, 기존 일정 수정·삭제는 변경 전후를 표시한다. 상단 ‘제안 기록’은 지난 제안을 다시 확인하는 보조 경로다. 제안 시간은 기기에 설정된 현지 시간대로 변환하고 GMT·UTC·IANA 표기를 화면에서 제거한다. 원본 ISO 시각과 승인 검증은 유지한다. 사용자 말풍선의 ‘나’ 헤더는 제거하고 본문만 표시하며 화면 판독기 구분은 유지한다.

PRD F07과 ADR-003은 명시 승인과 변경 범위 확인을 요구하며 별도 목록 이동을 요구하지 않는다. 디자인 전달본의 채팅 안 제안 카드 의도에 맞춘 UI 변경으로, 기존 제안 ID·버전·멱등·최신성 재검증 API를 재사용한다. 대화가 끝나거나 화면이 바뀌어도 미결 승인 요청을 임의로 버리지 않으며 연락 준비·발신은 기존 별도 승인 절차를 유지한다. 이 증분의 배포 여부는 구현 계획의 최신 기록을 따른다.

## 지연 제한·처리 결과 복구·빈 시간 계산 — 이전 증분

같은 `codex/preferences-chat-ux` 브랜치에서 기존 선호 UI 정리에 이어 다음을 구현했다. 이전의 ‘전체 deadline·상태 조회 미구현’은 이 증분 이전 상태다.

- 채팅 준비 과정은 기본120초로 제한한다. 모델·도구가 늦게 끝나도 후속 작업과 저장을 진행하지 않는다. 최종 DB 트랜잭션은 중도 포기하지 않으므로 DB 대기까지120초를 보장하지는 않는다.
- 결과 불명 오류에 ‘처리 결과 확인’을 제공한다. 인증된 원 요청·키로 읽기 조회하고, 검증된 저장 결과만 기존 답변/제안 경로로 복구한다. running·retryable·404·조회 실패는 신규 쓰기를 임의로 열지 않으며 원 요청 재시도를 유지한다. 특히 running에서도 lease 만료 후 회수할 수 있도록 동일 요청 재시도를 막지 않는다.
- 원 HTTP 오류는 성공으로 표시하지 않는다. completed의5xx 등 결과 불명 분류는 계속 보호되므로 반복되는 서버 장애의 강제 해제 UI는 없다. 앱 실행을 종료한 뒤 원 요청 식별자를 되찾는 영속 클라이언트 대기열은 이번 범위가 아니다.
- 서버에 사용자 메시지·도구 내용 없는 request/prepare/model/tool/finalize 경과와 모델/도구 호출수를 기록한다. 계측 추가는 실제 응답속도 향상 측정 결과가 아니다.
- `find_free_slots`는 스냅샷에서31일 이내 최대20개 빈 구간을 계산한다. 응답 전 현재 시각으로 필요한 길이가 남았는지 다시 확인하고 불충분한 원 후보가 있으면 재요청 안내로 돌린다. 사용자가 승인하기 전 일정은 변경하지 않는다.

검증: 최종 상태/deadline/빈 시간/클라이언트 분실 응답 복구 집중16개(skip0), 별도 격리 PostgreSQL 기존 멱등성3개(skip0), workspace typecheck·web export·diff 검사 통과. 모바일415개·도메인44개 통과와 API 전체 성공도 확인했으나 전체·집중 검사는 중복되므로 합산하지 않는다. PG는 독립 임시 DB에서 새 store/app 인스턴스·lease 회수·구 token 차단·완료 결과 재생을 확인했으며 실제 프로세스 kill 또는 운영 장애 복구 검증은 아니다. 실제 모델·제공자·기기 성능 측정은 하지 않았다. 기존 미리보기 서버와 공개 URL을 이 산출물로 교체하지 않았다.

모델·DB 교체, AI 인터뷰 저장 계약, AI 반복 규칙의 일괄 변경, 새 공유 캐시는 추가하지 않았다. 먼저 이 계측으로 실제 병목을 확인한다. 기존 수동 Calendar 동기화·증분 토큰과 반복 회차 생성 경로를 유지한다. 실제 제공자·실기기 성능 비교와 공개 배포는 별도다.

## 선호 화면 간소화·응답 대기 안내 — 최신 증분

작업 브랜치: `codex/preferences-chat-ux`. 기존 서버 정본·단일 Terra/high·사용자 승인·Memory 계약을 유지하는 화면 개선이다. 이 브랜치의 변경은 main 또는 공개 배포에 반영하지 않았다.

- AI 채팅의 중복 선호 진입을 제거하고 프로필의 ‘내 선호와 상황’으로 모았다. 저장 목록은 사람이 읽는 문장으로 표시하고 JSON·값 형식 선택·일반 목록 새로고침을 제거했다. 오류·충돌 복구에 필요한 재조회는 유지한다.
- 선호는 이름과 내용으로, 일시 상황은 내용과 사용자가 선택한 유효기간으로 입력한다. 기존 일반 텍스트는 목록의 명시적 수정으로 편집한다. 예약된 구조화 키를 텍스트로 덮어쓰지 않으며 알 수 없는 구조화값은 원문을 노출하지 않는다.
- 온보딩은 목표와 선호 시간대의 2단계로 줄였다. 기존 준비·이동·도착 여유 값은 null·0을 구분해 보존한다. 개별 시간 입력은 필수가 아니며 프로필 편집 안의 선택적 진입에서만 수정한다.
- 답변 준비 안내와 15초 경과 안내를 제공한다. 이는 실제 진행률이나 처리 단계가 아니다. 화면 이동이 요청 취소를 뜻하지 않음을 알리고, 기존 결과 불명·같은 요청 재시도·중복 쓰기 방지를 유지한다. 모델·API·DB 처리 속도를 개선한 것으로 해석하지 않는다.
- 신규 항목의 동명 덮어쓰기 방지는 현재 조회된 활성 fact 범위다. 만료·미래 fact까지 조건부 생성으로 보호하는 서버 계약은 이번에 추가하지 않았다. 일반 Memory 저장의 기존 kind/key upsert 의미는 유지한다.

검증: 모바일 전체 399개 통과 후 마지막 프로필·표시 유효성 보완을 적용했고, 최종 Memory/Profile/Chat·App/복구/연락 집중 170개(skip 0), 모바일 typecheck, web export, diff 검사를 통과했다. 전체/집중 검사는 겹치므로 합산하지 않는다. 별도 합성 API의 브라우저 미리보기에서 AI 선호 버튼 제거, 프로필→선호 진입, JSON 없는 입력·저장 후 문장 표시를 확인했다. 실제 사용자 데이터·모델·외부 API 호출 및 실제 기기 검증은 하지 않았다. 기존 사용자 앱·공개 배포는 유지한다.

### 비교 자료에서 취할 것과 후속 우선순위

비공개 Aria 분석 원문은 저장소에 추가하지 않는다. 관찰된 화면·설계 아이디어와 검증되지 않은 서버 구현·성능 추론을 구분한다. 과거 비교의 ‘PIKKU 4개 도구·Calendar 미정·undo 없음’은 현재 상태와 다르다. 현재 기본 4개 도구에 조건부 외부 조회 도구가 연결되고, Calendar 선택 가져오기·수동 동기화 및 completion/attendance 한 단계 undo가 있다. 일반 일정 변경 전체 undo는 없다.

| 순서 | 다음 개선 후보 | 기존 구현과 적용 경계 |
|---|---|---|
| 1 | 내용 없는 단계별 시간 계측, 전체 요청 deadline, 사용자별 처리 상태 조회 | 현재 호출별 60초·최대 10단계·클라이언트 180초는 전체 서버 deadline이 아니다. 취소·늦은 완료·lease·멱등 처리 계약을 먼저 맞춘다. |
| 2 | 서버의 순수 빈 시간 후보 계산 | LLM이 후보를 활용하되 같은 revision·시간대·충돌 검증과 사용자 승인을 유지한다. 도구 추가만으로 속도 향상을 단정하지 않는다. |
| 3 | 반복·대량 작업의 범위 제한 미리보기 | 직접 루틴 회차 생성 최대31일은 이미 있다. AI 반복 규칙 변경은 별도 미리보기·차이·승인 계약이 필요하다. |
| 4 | 측정 결과에 따른 중복 조회 합치기·캐시 | 사용자·권한·시간 범위·버전·TTL로 분리하고 승인 직전 최신 DB를 재검증한다. 날씨·지하철 캐시와 장소 실행 내 재사용은 이미 존재한다. |
| 5 | JSONB 조회·잠금·응답 크기 프로파일 | Calendar는 syncToken 증분 조회·etag 검사가 이미 있다. DB 교체나 전체 정규화를 선행하지 않고 병목 증거에 따라 인덱스·데이터 구조를 검토한다. |

위 후속 서버 개선은 이번 화면 작업에서 구현하지 않았다. 동일 시나리오의 p50/p95·모델 호출수·오류율과 stale/충돌 정확도를 함께 확인해야 한다. Aria의 실제 응답 속도나 서버 구조는 검증되지 않았으므로 성능 우위를 주장하지 않는다.

AI 인터뷰는 질문 → 사용자 답변 → 저장할 선호 요약 → 명시적 확인 → 기존 Memory 저장 순서가 후보이며 아직 구현하지 않았다. 현재 읽기 전용 Agent가 선호를 저장했다고 표현하거나 자연어를 임의의 숫자 시간값으로 변환하지 않는다.

## 초안 진입·제안 표시 보완 — 최신 증분

- 처리 중이거나 결과가 불명인 요청이 있어도 추가 화면에 들어가 초안을 작성할 수 있으며, 새 저장은 기존 요청 확인 전까지 차단한다.
- 제안 화면에서 내부 식별자·버전·생성 시각·검증 메타데이터를 숨기고, 전후 변경·판단에 필요한 필드·승인 경고는 유지한다.
- 기존 사용자 탭의 미확정 요청 보존을 위해 새로고침과 재시작을 하지 않았다. 실제 채팅 ledger 진단은 running 0건·retryable 1건이며 제공자 실패의 정확한 원인은 확인되지 않았다.
- 모델 호출 제한은 호출별 60초, Agent 최대 10단계, 클라이언트 180초다. 서버 전체 처리시간 제한과 독립 상태 조회는 구현되지 않았다.
- Gmail 발송·회신 통합 동의는 조사와 추천 단계이며 구현하지 않았다. 수정 요청 초안의 내부 ID·JSON은 별도 API context 부재로 현행을 유지하고, 긴 텍스트 8천 자 제한은 후속 과제다.

## 로그인·온보딩·프로필 통합 — 최신 증분

- **디자인 근거:** 00의 공식 Figma 도구 확인에서 메인 화면 일부(`2:862`, `28:852`)와 서브 파일의 온보딩 페이지(`97:2`) 접근에 성공했다. 카드 59개 인스턴스 전체를 직접 확인한 것은 아니다. 서브 디자인은 흐름 참고이며 기존 Pretendard·색상·캐릭터·공통 컴포넌트를 유지한다.
- **흐름과 저장:** Welcome, 실제 Google 회원 인증 경로, 3단계 선호 입력과 프로필을 연결했다. 선호는 기존 Memory의 사용자별 `planning_preferences` v1 preference로 저장한다. Agent 프롬프트는 사용자 출처의 선택값만 참고하도록 지시하며, 공통 Memory API는 일반 JSON을 받아 형식이나 모델 행동을 결정적으로 보장하지 않는다. 선호 조회·저장은 일정 자동 변경이 아니다. 상세 값과 리비전 경계는 [CONTRACTS](CONTRACTS.md)를 따른다.
- **검증:** 00이 전달한 최신 결과는 모바일 전체 **384개**, workspace typecheck, 최종 avatar 집중 **51개**, web export 통과다. Calendar 읽기 fallback 관련 합성 검사는 **18개** 통과했다. 이 집계는 서로 다른 검사 범위이므로 합산하지 않는다.
- **실제 제공자 확인:** 00이 기존 개발 계정의 연결 상태 4개와 실제 Calendar 목록 3개 조회를 확인했다. 이는 새 회원 로그인 성공이나 일정 쓰기 검증이 아니다.
- **로컬 실행:** `19006` 웹의 기본 API는 실제 회원 인증·영속 프로젝트 PostgreSQL을 사용하는 `19012`다. 기존 개발 연결 `19011`은 보존하고 합성 QA API `19009`는 별도다. 포트와 연결 상태는 확인 시점의 로컬 환경 기록이며 배포 주소가 아니다.
- **웹 회원 로그인 확인:** 실제 회원 로그인·온보딩 진입·Memory 조회를 확인했다. 읽기 전용 PostgreSQL 집계에서 회원과 유효 세션의 영속성 및 개발 계정과의 분리를 확인했다. 최초 OAuth의 `redirect_uri_mismatch` 원인은 확정되지 않았다.
- **남은 범위:** 신규 회원의 Calendar·Gmail은 각각 별도 권한 동의가 필요하다. 이번 증분의 iPhone·실제 전화 검증은 보류다. PR #17은 Draft로 미병합이며 이번 작업의 커밋·푸시·배포는 하지 않았다.

## 결합 원칙

- 기존 API client·hooks·mutation/operation guard와 화면 로직을 재사용하고 표시 부분을 교체한다. UI 안에 있는 상태 로직까지 지우거나 모든 로직이 이미 hook으로 분리됐다고 가정하지 않는다.
- 서버가 주는 제안 ID/버전·상태·충돌을 그대로 연결한다. 버튼 색이나 화면 전환만으로 저장/승인 성공을 표시하지 않는다.
- 진행 중·결과 불명 요청을 버리고 계정을 바꾸지 않는다. Calendar 실행 응답 유실은 같은 요청의 저장 결과 GET으로 확인하고 외부 쓰기를 다시 보내지 않는다.
- Pretendard, 기존 `Text`/`TextInput`, `ActionButton`, `GlassSurface`, `Icon`과 테마를 우선 사용한다. 새 Figma 자산/색·레이아웃은 실제 파일을 확인한 뒤 적용한다.
- 루틴 회차는 수동 생성 범위 최대31일이며 할 일/루틴 회차의 Google 내보내기는 현재 지원하지 않는다. 공유 일정의 원본 시간 반영은 이미 적용된 연락 합의와 정확한 원본·권한 증거가 있을 때만 허용한다.
- 통화 전용 프롬프트는 팀원 브랜치 검수 후 현재 디자인 브랜치에 병합했다. ClawOps에 저장된 Agent 반영과 실제 통화 검증은 별도다.

구현 중 발견한 복구 초안 key 회귀, AI의 변경 없는 로컬 필드가 변경된 ISO 제안을 가리는 문제, event→task→event 전환에서 옛 참석 undo가 되살아나는 문제를 수정했다. 원격 Calendar 삭제도 상태 이력을 같은 트랜잭션에서 정리한다. 새 `statusUndo`를 저장한 뒤 구 strict decoder 서버와 혼용/코드 단독 롤백은 할 수 없다.
