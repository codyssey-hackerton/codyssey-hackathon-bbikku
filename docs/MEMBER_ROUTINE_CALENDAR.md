# 회원·반복 루틴·Calendar 쓰기 연결

2026-11-01 사용자 요청으로 기존 시연 기능에 추가한 구현이다. 기존 참여 코드/개발 토큰, 전화·워치 기능을 보존한다. 실제 Google 신규 로그인/쓰기 동의와 개인 캘린더 변경은 자동 테스트로 대신했다고 하지 않는다.

## 회원 가입·로그인

설정에서 Google 로그인/가입을 시작하고 외부 브라우저의 확인 코드를 원래 앱에 입력한다. 기존 Google 웹 OAuth 클라이언트와 `/v1/google/oauth/callback`을 재사용하며 회원 state는 `member_` 접두사로 연결 동의와 분리한다. 로그인 scope는 `openid email profile`이며 Calendar/Gmail 권한을 함께 요구하지 않는다.

공식 `google-auth-library`로 ID token 서명·대상 client·발급자·만료를 검증하고 nonce·sub·검증된 이메일을 확인한다. PKCE/state와 앱 비밀값/일회 확인 코드가 결합돼야 회원과 7일 세션을 만든다. 동일 Google sub는 같은 회원이고 이메일만 같다는 이유로 계정을 합치지 않는다. 기존 preview 사용자의 일정/Google 연결을 새 회원에게 자동 이관하지 않는다.

세션 원문은 앱 메모리에만, 서버에는 해시만 저장한다. 앱을 다시 시작하면 다시 로그인하며, 로그아웃은 해당 세션을 서버에서 취소한다. 로그인·계정 변경은 처리 결과가 미확정인 요청이 없어야 하며 기존 화면 캐시를 지운다. OAuth 진행 상태와 IP 제한은 인스턴스 메모리이므로 재시작 시 새 흐름이 필요하고 여러 인스턴스에 공유되지 않는다. 현재 단일 API 프로세스를 전제로 한다.

## 반복 루틴

루틴 화면에서 이름·요일(월=1~일=7)·시간대·시작일·현지 시작시각·소요시간을 등록한다. 매일은 요일 7개를 선택한다. 수정/비활성과 회차 생성은 별도다.

- 생성 범위는 기본 선택일 하루이며 시작일~종료일을 최대 31일로 지정한다. **회차 생성 버튼**을 누르면 기존 일정 검증 경로로 개인 고정 시간 task를 만든다. 무기한 자동 생성/백그라운드 루틴 실행은 이번 구현이 아니다.
- 회차는 하루·월간 화면에 표시하고 기존 완료/미완료 체크인을 사용한다. 규칙을 수정/비활성화해도 이미 생성한 과거·미래 회차는 유지한다. 현재 회차를 바꾸려면 일정 화면에서 직접 수정한다.
- 동일 사용자·루틴·날짜는 한 번만 생성한다. 삭제한 회차도 다시 자동 생성하지 않는다. `existingCount`는 삭제된 것을 포함한 이전 생성 회차 수이지 현재 남은 일정 수가 아니다.
- 충돌 회차와 DST의 없거나 모호한 시각은 만들지 않고 사유를 반환한다. 다른 일정을 임의로 옮기지 않는다. DST 검증은 현재 시간대의 오프셋 후보를 역검증하며 모든 TZDB 역사적 전환에 대한 형식적 보장은 아니다.
- 규칙·회차·요청 멱등 기록과 일정/sourceRef는 같은 PostgreSQL 트랜잭션으로 커밋/롤백한다.

## Google Calendar 원본 쓰기·양방향 동기화

Google 연결 화면에서 **Calendar 쓰기**에 별도로 동의한다. 기존 읽기 자격은 유지하며 쓰기 자격은 별도 파일로 보관한다. 같은 웹 클라이언트를 사용하고 `calendar.events` 권한이 새로 필요하다. 기존 읽기 동의만으로 쓰지 않는다.

1. 쓰기 가능한 캘린더를 선택하고 삐꾸에서 내보낼 개인 이벤트를 직접 선택한다(최대 100개). 모든 개인 일정을 모든 캘린더에 자동 전파하지 않는다.
   이미 연결한 캘린더에 나중에 만든 개인 이벤트를 내보내려면 그 캘린더를 선택하고 **선택 일정 추가**로 대기열에 넣은 뒤 동기화를 실행한다. 기존 연결/매핑은 유지하며 추가 선택 자체는 Google 쓰기를 실행하지 않는다.
2. 삭제 전파는 기본 꺼짐이다. 명시적으로 켠 경우에만 연결된 일정의 양방향 삭제를 허용한다. 연결 저장 자체는 동기화 실행이 아니다.
3. 동기화 실행 버튼을 누르면 Google 변경을 가져오고 연결된 삐꾸 변경을 Google에 반영한다. **수동 양방향 동기화**이며 실시간 webhook·주기 자동 동기화는 아니다.
4. 양쪽 동시 변경·계정/원본 바인딩 불일치·충돌은 검토 대상으로 보존한다. 공유 약속은 기존 연락/수락 경계를 우회해 수정하지 않는다. 종일·반복 Google 이벤트와 기타 미지원 형식은 개수/사유로 표시한다.
5. 동기화 연결해제는 원본/내부 일정을 삭제하지 않는다. 같은 요청의 외부 쓰기를 자동 재전송하지 않는다.

증분 syncToken과 페이지를 사용하며 410은 전체 재조회한다. 쓰기는 결정적 event ID·pIKKU 바인딩과 ETag/If-Match를 사용한다. 다른 참석자를 추가하지 않고 `sendUpdates=none`으로 실행한다. 삭제는 opt-in 외에도 저장된 삭제 revision/개인 일정 증거가 baseline과 맞아야 한다. 과거 자료에 삭제 증거가 없거나 중간 변경 후 삭제됐으면 검토 대상으로 둔다.

연락 합의가 이미 내부 일정에 적용된 **기존 공동 약속의 시간 변경**은 제한적으로 원본에 반영할 수 있다. 저장된 사용자 연락 승인·선택 대안·검증/확인된 응답, 정확한 현재 일정/원본 sourceVersion, 변경 전 제목·시간과 원격 ETag가 일치해야 한다. 선택 Calendar owner 및 Google 주최 계정 일치도 확인한다. `organizer.self`만으로 사용자가 주최자라고 판단하지 않는다. 새 공동 이벤트 내보내기·공동 삭제·타인 주최·원격에서 바뀐 공동 약속은 이 경로로 처리하지 않는다. 외부 참석자 전체의 합의나 각 참석자 Calendar로의 전파를 보장하는 기능도 아니다.

증분 결과가 비어도 이후 합의된 미매핑 공동 약속은 유효 증거가 있는 원본만 별도 재조회한다(실행당 최대100개). 증거 없음/다른 계정은 조회 대상으로 넣지 않으며 상한 초과는 충돌로 표시한다. Google 쓰기 뒤 원본 버전도 함께 갱신해 후속 합의를 옛 버전으로 판단하지 않는다.

원격 쓰기 직전부터 확정까지 같은 사용자의 DB 잠금을 유지해 다른 일정 변경과 경합하지 않게 한다. Google 네트워크 동안 해당 사용자의 작업이 대기할 수 있다. 외부 HTTP와 DB commit, OAuth 자격 파일 교체는 하나의 원자 트랜잭션이 아니며 파일/계정 교체 경계를 재검증한다. 중단/결과 불명은 `review_required`로 보존한다. 별도 조정 없이 불명 작업을 해제/재전송하지 않는다. 정상 완료 뒤 응답만 유실된 경우는 저장된 작업 결과를 읽기 전용으로 확인한다.

동기화 실행은 자체 영속 작업 ledger로 보호하며 요청 멱등 실행기의 바깥 DB 트랜잭션으로 전체를 감싸지 않는다. 별도 sync-row 커밋이 같은 연결의 미완료 잠금을 기다리던 자기 잠금 문제를 실제 HTTP/PG 통합 검사로 재현·수정했다. Calendar 실행은 lease가 만료됐다는 이유로 자동 재실행할 수 있는 작업 목록에도 넣지 않는다.

## 실행·사용자 준비

기존 `.env.local`의 `PIKKU_DATABASE_URL`, `PIKKU_GOOGLE_OAUTH_CLIENT_ID`, `PIKKU_GOOGLE_OAUTH_CLIENT_SECRET`, `PIKKU_GOOGLE_OAUTH_REDIRECT_URI`, 사용자별 비공개 자격 디렉터리 설정을 사용한다. 새 API 제공자 키는 필요하지 않다. 비밀값은 앱의 공개 환경 변수나 Git에 넣지 않는다. PostgreSQL 없이 실행하면 회원/루틴/동기화 저장 기능은 미설정으로 응답한다.

```sh
npm ci
npm run dev:local -- --postgres --scheduler
```

실제 사용자는 Google 회원 로그인 후 필요한 외부 연결을 각각 동의해야 한다. Google Cloud 테스트 앱이면 해당 Google 계정이 테스트 사용자에 등록돼야 하고 Calendar API/쓰기 권한 동의도 필요하다. 기존 시연 계정 자료를 사용하려면 별도 이관 정책이 필요하다.

## DB 변경과 배포 경계

기존 사용자 일정 JSONB를 보존하고 회원/세션·루틴/회차/요청·동기화 연결/작업용 테이블을 추가한다. 서버 시작 시 CREATE IF NOT EXISTS 마이그레이션을 실행한다. 외부 효과 재전송에 DB 재시도를 그대로 적용하지 않는다.

새 `tombstones` 필드는 과거 문서에서는 생략/빈 Map으로 읽지만 새 삭제 기록이 저장된 문서는 구 strict decoder가 거부한다. 같은 DB에 구·신 API/예약 프로세스를 혼용하거나 코드만 구버전으로 되돌리면 안 된다. 기존 백업·동시 전환/복원 절차를 따른다. 이번 구현 작업에서 운영 DB·계정·공개 배포는 변경하지 않았다.

검증은 격리 PostgreSQL 포함 API 485/485, 모바일 합성 311/311, 도메인 44/44와 workspace typecheck, 검증용 web export를 확인했다. 실제 Google 신규 동의·개인 캘린더 쓰기, 실기기 확인은 남아 있다. 이 기록을 운영에서의 실제 실행 성공으로 확대하지 않는다.
